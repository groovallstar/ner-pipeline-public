# 한·일·베 NER 데이터셋의 표현 방식 비교 — KLUE / Stockmark / WikiANN
## 1. NER 정의

**NER (Named Entity Recognition, 개체명 인식)** 은 문장 속에서 "사람 이름", "회사 이름", "장소" 같은 **특별한 의미가 있는 단어**를 찾아내는 작업이다. 예:

> "**삼성전자**는 **2024년 3월**에 **서울**에서 행사를 열었다."
> → 삼성전자 (회사), 2024년 3월 (날짜), 서울 (장소)

이 문서는 한국어(KLUE), 일본어(Stockmark), 베트남어(WikiANN vi) 세 NER 데이터셋이 **데이터를 어떤 방식으로 표현·처리하는지**를 비교·설명한다.

## 2. 한눈에 보는 비교표

| 항목 | 🇰🇷 KLUE NER | 🇯🇵 Stockmark NER | 🇻🇳 WikiANN (vi) |
|------|---------------|-------------------|------------------|
| 정식 명칭 | KLUE Benchmark - NER | stockmark/ner-wikipedia-dataset | unimelb-nlp/wikiann (config=vi) |
| 만든 곳 | 한국 산학 컨소시엄 (31명 저자, NeurIPS 2021) | 일본 Stockmark 사 (AI 스타트업) | Pan et al. 2017 (ACL), 멜버른대 관리 |
| 원본 데이터 출처 | 위키트리 뉴스 + 에어비앤비 리뷰 | 일본어 위키백과 | 베트남어 위키백과 (다국어 WikiANN의 vi 서브셋) |

## 3. 엔티티(개체) 종류 비교

### 🇰🇷 KLUE — 6종 (짧은 영어 약어)

| 태그 | 뜻 | 쉬운 예시 |
|------|-----|----------|
| PS | 사람 | 김철수, BTS |
| LC | 장소 | 서울, 한강 |
| OG | 기관/회사 | 삼성전자, 경찰 |
| DT | 날짜 | 2024년, 어제 |
| TI | 시간 | 오후 2시, 새벽 |
| QT | 수량/숫자 | 100명, 50억원 |

### 🇯🇵 Stockmark — 8종 (canonical 영문 축약)

HuggingFace `stockmark/ner-wikipedia-dataset`의 원본 라벨은 일본어
(`人名`/`法人名`/`地名`/…)이지만, 본 저장소의 파이프라인은
**canonical 영문 축약**으로 통일해 사용한다 (매핑 정의:
`docs/manual/data/canonical-entity-schema.md`).

| 태그 | 뜻 | 쉬운 예시 |
|------|-----|----------|
| PER (인명) | 사람 | 織田信長 (오다 노부나가) |
| CORP (법인명) | **회사**, 철도사, 방송국 | トヨタ自動車 (토요타) |
| LOC (지명) | 나라, 도시, 자연물 | 東京, 富士山 |
| FAC (시설명) | **건물**, 역, 공항, 학교, 병원 | 東京タワー, 東京駅 |
| PROD (제품명) | 상품, 서비스, 작품명 | iPhone, プリウス |
| EVT (이벤트명) | 대회, 사건, 전쟁 | オリンピック |
| POL (정치 조직) | 정부, 정당, 군대, 법원 | 自民党, 米軍 |
| ORG (기타 조직) | 대학, 스포츠팀, 협회 | 早稲田大学, FIFA |

### 🇻🇳 WikiANN vi — 3종 (영어 약어)

| 태그 | 뜻 | 쉬운 예시 |
|------|-----|----------|
| PER | 사람 | Nguyễn Xuân Phúc, Hồ Chí Minh |
| LOC | 장소 | Hà Nội, Việt Nam, Sông Mekong |
| ORG | 기관/조직 | Samsung, Đảng Cộng sản Việt Nam |

### 핵심 차이 — "조직"을 얼마나 세분화하느냐

- **WikiANN (3종)**: PER / LOC / ORG — 가장 단순. 모든 조직을 `ORG` 하나로 합친다.
- **KLUE (6종)**: 조직을 `OG` 하나로 두지만, 대신 **DT·TI·QT** (날짜·시간·수량) 범주를 별도로 가진다.
- **Stockmark (8종)**: 조직을 **CORP / FAC / POL / ORG** 4개로 쪼개고, **이벤트·제품**도 별도 범주로 구분한다.

예: "토요타 본사 건물"이라 하면
- WikiANN 스타일: 토요타 = ORG, 본사 건물 = LOC
- KLUE 스타일: 토요타 = OG, 본사 건물 = LC
- Stockmark 스타일: 토요타 = CORP, 본사 건물 = FAC

## 4. BIO 태그란?

**BIO 태깅**은 여러 토큰에 걸친 엔티티를 표현하는 표준 방식이다. 각 토큰에 3종류의 태그 중 하나를 붙인다.

| 태그 | 의미 | 역할 |
|------|------|------|
| **B-**XXX | **B**egin | 엔티티의 **시작** 토큰 |
| **I-**XXX | **I**nside | 엔티티의 **중간·끝** 토큰 (바로 앞 B- 또는 I-에 이어짐) |
| **O** | **O**utside | 엔티티가 **아닌** 일반 토큰 |

`XXX`에는 엔티티 타입이 들어간다 (`B-PS`, `I-LC`, `B-OG` 등).

### 예시

```
문장:  김  철  수  는  서  울  에  살  다
태그:  B-PS I-PS I-PS  O  B-LC I-LC  O  O  O
엔티티: └──── 김철수 (PS) ────┘  └ 서울 (LC) ┘
```

### 왜 B-와 I-를 나눌까?

**연속된 같은 타입의 엔티티를 구분**하기 위해서다. 예를 들어 "김철수 이영희"(두 사람)는 `B-PS I-PS I-PS B-PS I-PS I-PS`가 되어, 두 번째 `B-PS`로 **새로운 인물**이 시작됨을 알 수 있다. 만약 B가 없고 I만 쓰면 "김철수이영희"를 한 사람으로 오인하게 된다.

### BIO 시퀀스 → 엔티티 추출하기

반대로 BIO 태그 줄을 읽어 엔티티를 뽑아내는 규칙은 매우 단순하다.

1. `B-XXX`를 만나면 → **새로운 XXX 엔티티 시작**
2. 바로 이어지는 `I-XXX`는 → **같은 엔티티에 이어 붙이기**
3. `O` 또는 **다른 B-** 를 만나면 → **현재 엔티티 종료**

예시:

```
태그:   B-PS I-PS I-PS  O  B-LC I-LC  O  B-OG I-OG
토큰:   김   철   수   은  서   울   의  경   찰
추출:   └─ 김철수(PS) ─┘   └ 서울(LC) ┘    └ 경찰(OG) ┘
```

타입이 바뀌면(`I-LC` 뒤에 `B-OG`) 자동으로 새 엔티티로 잘리고, `O`가 나오면 바로 끊긴다. 이 규칙이 있기에 **여러 개의 엔티티가 뒤섞인 문장도 모호함 없이** 복원할 수 있다.

### BIO 변형

- **BIO (IOB1)**: 원조. 같은 타입 엔티티가 인접할 때만 B를 사용.
- **IOB2**: 모든 엔티티의 첫 토큰에 B를 사용. **현대 표준**이며 KLUE·WikiANN 모두 이 형식.
- **BIOES / BILOU**: End/Single 태그 추가. 정확도↑, 태그 수↑.

## 5. 데이터 형식 차이 — 음절 BIO / 단어 BIO / 문자 오프셋

### 🇰🇷 KLUE — 음절 단위 BIO 태그

한 글자(음절)마다 태그를 단다. **공백도 한 토큰으로** 취급한다.

```
토큰:  영  동  고  속  도  로  ␣  강  릉
태그:  B-LC I-LC I-LC I-LC I-LC I-LC  O  B-LC I-LC
```

- `B-LC` = 장소 엔티티의 **시작(Begin)**
- `I-LC` = 장소 엔티티의 **내부(Inside)**
- `O` = 개체명 아님(Outside)

### 🇯🇵 Stockmark — 문자 오프셋 span

문장은 그대로 두고, "몇 번째 글자부터 몇 번째까지가 뭐다"를 별도로 기록한다.

```json
{
  "text": "織田信長は安土城を建て、本能寺の変で明智光秀に討たれた。",
  "gold_spans": [
    {"text": "織田信長",   "type": "PER",       "start": 0,  "end": 4},
    {"text": "安土城",     "type": "FAC",     "start": 5,  "end": 8},
    {"text": "本能寺の変", "type": "EVT", "start": 11, "end": 16},
    {"text": "明智光秀",   "type": "PER",       "start": 17, "end": 21}
  ]
}
```

### 🇻🇳 WikiANN vi — 단어 단위 BIO 태그

공백으로 분리된 단어마다 태그를 단다. 공백은 **별도 토큰이 아니다** (KLUE와의 큰 차이).

```
토큰:  Nguyễn  Văn   A     sinh  ra  tại  Hà    Nội
태그:  B-PER   I-PER I-PER O     O   O    B-LOC I-LOC
엔티티: └─── Nguyễn Văn A (PER) ───┘        └ Hà Nội (LOC) ┘
```

### 왜 이런 차이가 날까?

세 언어는 **띄어쓰기 관습**이 전혀 달라서, 각 데이터셋이 가장 편한 단위를 골랐다.

- **한국어(KLUE)**: 조사가 단어에 달라붙는다("서울**에서**"). 음절로 쪼개면 "서울"과 "에서"를 깔끔하게 분리해 태깅할 수 있어 **음절 BIO**를 쓴다.
- **일본어(Stockmark)**: 띄어쓰기가 **없고** 형태소 경계도 모호하다. 원문은 그대로 두고 "문자 몇 번째 ~ 몇 번째"를 지정하는 **문자 오프셋** 방식이 가장 자연스럽다.
- **베트남어(WikiANN)**: 영어처럼 **공백으로 단어가 확실히 분리**된다. 단어 하나가 기본 단위가 되므로 **단어 BIO**가 가장 직관적이다.

## 6. 나란히 보는 실제 샘플

비슷한 의미의 문장("X가 Y에서 Z회사의 행사에 참석했다")을 세 데이터셋 형식대로 표현하면 이렇게 다르다.

### 🇰🇷 KLUE — 음절 BIO

```
문장: 김연아가 서울에서 삼성전자 행사에 참석했다
토큰: 김 연 아 가 ␣ 서 울 에 서 ␣ 삼 성 전 자 ␣ 행 사 에 ␣ 참 석 했 다
태그: B-PS I-PS I-PS O O B-LC I-LC O O O B-OG I-OG I-OG I-OG O O O O O O O O O
```
특징: 조사 "가", "에서"는 엔티티 밖(`O`)으로 깔끔히 분리된다. 공백도 한 토큰.

### 🇯🇵 Stockmark — 문자 오프셋

```json
{
  "text": "羽生結弦が東京でトヨタ自動車のイベントに出席した。",
  "gold_spans": [
    {"text": "羽生結弦",       "type": "PER",   "start":  0, "end":  4},
    {"text": "東京",           "type": "LOC",   "start":  5, "end":  7},
    {"text": "トヨタ自動車",   "type": "CORP", "start":  8, "end": 14}
  ]
}
```
특징: 원문을 자르지 않고 그대로 두며, **문자 인덱스**로 엔티티 위치를 기록한다.

### 🇻🇳 WikiANN — 단어 BIO

```
문장: Nguyễn Xuân Phúc đã tham dự sự kiện của Samsung tại Hà Nội
토큰: Nguyễn   Xuân    Phúc    đã sự dự kiện của Samsung  tại Hà    Nội
태그: B-PER    I-PER   I-PER   O  O  O  O    O   B-ORG    O   B-LOC I-LOC
```
특징: 단어 단위라서 가장 읽기 쉽다. 베트남어는 성/이름 각 음절을 공백으로 띄어 써서 자연스럽게 `B-I-I` 구조가 만들어진다.

## 7. 세 형식의 장단점

| 항목 | 음절 BIO (KLUE) | 단어 BIO (WikiANN) | 문자 오프셋 (Stockmark) |
|------|-----------------|---------------------|--------------------------|
| **읽기 쉬움** | △ 음절이 너무 작음 | ◎ 단어가 의미 단위 | ○ 원문 유지·주석만 별도 |
| **저장 효율** | △ 토큰 수 多 | ◎ 토큰 수 少 | ◎ 태그 줄 불필요 |
| **조사·접사 처리** | ◎ 깔끔히 분리 | △ 조사가 단어에 붙음 | ○ 오프셋으로 잘라냄 |
| **경계 모호 언어(일본어)** | ✕ 형태소 분석 필요 | ✕ 띄어쓰기 없음 | ◎ 문자 단위라 무관 |
| **중첩 엔티티** | ✕ 불가 (한 토큰=한 태그) | ✕ 불가 | ◎ 여러 span 겹침 가능 |
| **엔티티 중복 처리** | ○ 위치 자동 구분 | ○ 위치 자동 구분 | △ 같은 문자열 반복 시 인덱스로만 구분 |
| **전처리 부담** | 音절 분리 필요 | 공백 split만 | 원문 그대로 |
| **도구 호환성** | seqeval 등 BIO 도구 | seqeval 등 BIO 도구 | 자체 매칭 로직 필요 |

요약하면 — **BIO 계열**은 표준 도구가 많아 편하지만 중첩 엔티티를 표현하지 못하고, **문자 오프셋**은 유연하지만 평가/변환 로직을 직접 짜야 한다.

## 8. 도메인과 문체 차이

같은 NER 작업이라도 **어떤 글에서 문장을 뽑았는지**에 따라 등장하는 엔티티의 성격이 달라진다.

| 데이터셋 | 출처 | 문체 | 특징적 엔티티 경향 |
|----------|------|------|---------------------|
| KLUE NER | 위키트리 **뉴스** + 에어비앤비 **리뷰** | 격식 뉴스 + 구어체 리뷰 혼재 | 날짜·시간·수량(DT/TI/QT)이 많이 등장. 뉴스 특성상 "어제", "오후 2시" 같은 상대 표현이 흔함 |
| Stockmark NER | 일본어 **위키백과** | 백과 문어체 | 역사 인물·시설·이벤트(전쟁·조약)가 풍부. 한 문장에 여러 엔티티가 촘촘하게 나열되는 경향 |
| WikiANN (vi) | 베트남어 **위키백과** (자동 정렬 기반) | 백과 문어체 | 고유명사(사람·지명·조직) 위주. 다만 자동 생성 데이터라 **노이즈가 상대적으로 많음** |

도메인이 비슷하면(둘 다 위키백과: Stockmark/WikiANN) 엔티티 분포가 유사하고, 도메인이 다르면(뉴스·리뷰인 KLUE) 시간/수량 같은 범주 비중이 커진다. 같은 언어라도 **뉴스 데이터에서 학습한 모델을 SNS 글에 그대로 쓰면 성능이 떨어지는** 이유가 여기에 있다.
