## 1. 재구축 단계 개요

파이프라인을 처음부터 다시 구축하거나, 새 언어/데이터셋으로 확장할 때 아래 순서를 따른다. 각 단계는 이전 단계의 출력에 의존하므로, **반드시 순서대로 진행**해야 한다.

| 단계 | 이름 | 핵심 산출물 | 주요 코드 |
|------|------|------------|-----------|
| 1 | 데이터셋 선정 및 준비 | `List[NERRecord]` | `src/labelers/dataset_loader.py` |
| 2 | 엔티티 타입 정의 | 태그 목록 + 정의 문서 | 예: `src/labelers/ko/ner_prompts.py:11` |
| 3 | 프롬프트 설계 | 프롬프트 템플릿 (규칙 + 예시 + 출력 형식) | 예: `src/labelers/ko/ner_prompts.py` |
| 4 | LLM 선정 및 설정 | LLM 인스턴스 (모델, temperature, JSON mode) | 예: `src/labelers/ko/vllm_ner_labeler.py` |
| 5 | 파싱 및 후처리 | spans 리스트 + BIO 태그 | 예: `src/labelers/ko/vllm_ner_labeler.py` |
| 6 | 반복 개선 | 개선된 프롬프트/설정 | (Step 2~5 반복) |

> **주의**: 평가 파이프라인(메트릭 구축 및 실행)은 재설계 중이며 이 가이드에서 제외되었다. 재구축된 방법이 확정된 후 다시 문서화한다.

## 2. 단계별 의존관계 다이어그램

```
Step 1: 데이터셋 선정 및 준비
    │
    ▼
Step 2: 엔티티 타입 정의 ◄─────────────────────────────┐
    │                                                    │
    ▼                                                    │
Step 3: 프롬프트 설계 ◄──────────────────────┐          │
    │                                         │          │
    ▼                                         │          │
Step 4: LLM 선정 및 설정                      │          │
    │                                         │          │
    ▼                                         │          │
Step 5: 파싱 및 후처리                         │          │
    │                                         │          │
    ▼                                         │          │
Step 6: 반복 개선 ────────────────────────────┘──────────┘
    │         (결과 분석 후 해당 단계로 롤백)
    │
    ▼
  완료
```

**의존 관계 요약:**
- Step 1 → Step 2: 데이터셋의 어노테이션 가이드라인이 엔티티 타입을 결정한다
- Step 2 → Step 3: 엔티티 타입 정의가 프롬프트의 규칙과 예시를 결정한다
- Step 3 → Step 4: 프롬프트 형식이 LLM 설정(JSON mode 등)에 영향을 준다
- Step 4 → Step 5: LLM 출력 형식이 파싱 로직을 결정한다
- Step 6 → Step 2~5: 평가 결과에 따라 어느 단계든 롤백할 수 있다

## 3. Step 1: 데이터셋 선정 및 준비

### 입력

- 데이터셋 선택 기준 (언어, 도메인, 엔티티 타입 수)

### 출력

- `List[NERRecord]` — `{tokens, ner_tags, id, sentence?}` 형태
- 토큰화 방식 이해 (대상 언어/데이터셋에 따라 다름)

### 작업 내용

1. **데이터셋 선택**: 목적에 맞는 NER 데이터셋을 선정한다
   - 예시 — 한국어 파이프라인의 경우: KLUE NER (6 엔티티 타입, 음절 토큰화)
   - HuggingFace에서 로딩하거나 JSONL로 사전 export
2. **로딩 경로 확인**: `DatasetLoader.load()` (`src/labelers/dataset_loader.py:35-62`)
   - JSONL 폴백 경로: 데이터셋별로 지정 (예: `/data/ner/klue/validation.jsonl`)
   - HuggingFace 경로: 예) `load_dataset("klue", "ner", split="validation")`
3. **토큰화 방식 파악**: 대상 언어/데이터셋에 따라 토큰화 단위가 다르다

   > **언어별 주의사항**: 토큰화 방식은 대상 언어와 데이터셋에 따라 달라진다. 이후 단계(특히 Step 5의 BIO 변환)는 이 방식에 맞춰 구현해야 한다.

   - 예시 — 한국어(KLUE NER): 음절(syllable) 단위 토큰화
     - 각 한글 음절이 하나의 토큰: `["경", "찰", "은"]`
     - 단어 사이 공백은 빈 문자열 토큰: `["경", "찰", "은", " ", "박", ...]`

4. **ClassLabel 변환 확인**: HuggingFace 정수 라벨 → 문자열 태그 자동 변환 (`dataset_loader.py:83-99`)
5. **`sentence` 필드 보존 확인**: 원본 문장이 있으면 그대로 사용 (`dataset_loader.py:102-104`)

### 체크포인트

- [ ] `DatasetLoader.load(...)` 호출 시 `List[NERRecord]`가 반환되는가
- [ ] 반환된 record의 `tokens`가 예상 토큰화 방식인가
- [ ] `ner_tags`가 문자열 태그(`"B-PS"`, `"O"` 등)인가 (정수가 아닌)
- [ ] `sentence` 필드가 존재하고, 원본 문장을 담고 있는가
- [ ] `max_samples` 파라미터로 샘플 수 제한이 정상 동작하는가

```python
# 체크포인트 검증 코드 (예시 — 한국어 파이프라인의 경우)
from labelers.dataset_loader import DatasetLoader
loader = DatasetLoader()
records = loader.load("klue", "ner", max_samples=5)
for r in records:
    print(r["id"], r["tokens"][:10], r["ner_tags"][:10])
    print("sentence:", r.get("sentence", "없음")[:50])
```

### 실패 패턴

| 증상 | 원인 | 조치 |
|------|------|------|
| `DatasetNotFoundError` | HuggingFace 접근 불가 / 데이터셋명 오류 | JSONL 폴백 파일 준비 |
| `ner_tags`가 정수 리스트 | ClassLabel 변환 누락 | `dataset_loader.py`의 ClassLabel 변환 로직 확인 |
| `tokens`가 예상과 다른 단위 | 데이터셋이 다른 토큰화 사용 | 토큰화 방식에 맞게 이후 단계 조정 필요 |
| `sentence` 필드 없음 | 데이터셋에 원본 문장 미포함 | `TagAligner.reconstruct_text()` 폴백 사용 |

### 롤백 조건

이 단계로 돌아와야 하는 경우:
- 데이터셋의 어노테이션 품질이 낮아 gold standard를 신뢰할 수 없을 때
- 토큰화 방식이 이후 단계(특히 Step 5의 BIO 변환)와 호환되지 않을 때
- 평가(Step 6)에서 gold 데이터 자체의 일관성 문제가 발견될 때

## 4. Step 2: 엔티티 타입 정의

### 입력

- Step 1에서 파악한 데이터셋의 어노테이션 가이드라인
- 데이터셋에 정의된 엔티티 태그 목록

### 출력

- 엔티티 타입 목록 (코드 내 상수)
- 각 타입의 정의, 범위, 경계 사례 문서

### 작업 내용

1. **태그 목록 정의**: 언어/데이터셋별 `DEFAULT_ENTITY_TYPES` 상수로 관리

   예시 — 한국어 파이프라인의 경우 (`src/labelers/ko/ner_prompts.py:11`):
   ```python
   DEFAULT_ENTITY_TYPES = ["PS", "LC", "OG", "DT", "TI", "QT"]
   ```

2. **각 태그의 의미와 범위를 명확히 문서화**:

   예시 — 한국어(KLUE NER) 태그 정의:

   | 태그 | 의미 | 범위 | 경계 사례 |
   |------|------|------|-----------|
   | PS | 인명 | 사람 이름, 성만도 가능, 아이돌 그룹명 | "BTS", "소녀시대" → PS |
   | LC | 지명 | 장소, 지역, 국가, 건물, 시설 | 복합 지명은 전체를 하나로 |
   | OG | 기관명 | 회사, 기관, 단체, 정당, 팀 | "경찰" → 기관 맥락이면 OG |
   | DT | 날짜 | 연도, 월, 일, 기간, 상대날짜, 시대 | "5공화국시절" → DT |
   | TI | 시간 | 시각, 시간대, 경과시간 | "새벽" 단독 → TI |
   | QT | 수량 | 숫자+단위, 금액, 비율, 순서 | "첫번째" → QT |

3. **태그 정규화 매핑 정의**: LLM이 다른 형식으로 출력할 수 있으므로 정규화 필요

   예시 — 한국어 파이프라인의 경우:
   ```
   PER → PS,  LOC → LC,  ORG → OG
   DATE → DT, TIME → TI, QUANTITY → QT
   ```
   코드: `normalize_tag()` (`src/labelers/tag_aligner.py:44-59`)

   > 다른 언어를 추가할 때는 해당 데이터셋의 태그 체계에 맞는 정규화 매핑을 별도로 정의한다.

### 체크포인트

- [ ] 데이터셋의 모든 태그가 정의 목록에 포함되어 있는가
- [ ] 각 태그의 경계 사례가 문서화되어 있는가
- [ ] 태그 정규화 매핑이 LLM이 출력할 수 있는 변형을 모두 커버하는가
- [ ] gold 데이터에서 각 태그의 분포(빈도)를 확인했는가

```python
# 체크포인트 검증 코드: 태그 분포 확인
from collections import Counter
tag_counts = Counter()
for r in records:
    for t in r["ner_tags"]:
        if t != "O":
            tag_counts[t.split("-")[1]] += 1
print(tag_counts)
```

### 실패 패턴

| 증상 | 원인 | 조치 |
|------|------|------|
| 특정 엔티티 F1이 극도로 낮음 | 해당 태그의 정의가 모호 | 정의를 구체화하고 프롬프트에 반영 |
| LLM이 정의에 없는 태그 출력 | 태그 목록이 불완전 | 정규화 매핑 추가 또는 프롬프트에서 명시적 제한 |
| 태그 간 혼동 빈번 | 태그 경계가 불명확 | 경계 사례 규칙을 추가 |

### 롤백 조건

이 단계로 돌아와야 하는 경우:
- Step 6 평가에서 특정 엔티티 타입의 성능이 지속적으로 저조할 때
- 프롬프트 규칙(Step 3)을 아무리 조정해도 특정 태그의 정의 자체가 문제일 때
- 새로운 엔티티 타입을 추가하거나 기존 타입을 분할/병합해야 할 때

## 5. Step 3: 프롬프트 설계

### 입력

- Step 2에서 정의한 엔티티 타입 목록
- 각 타입의 정의, 범위, 경계 사례

### 출력

- 프롬프트 템플릿 (시스템 프롬프트 + 규칙 + Few-shot 예시 + 출력 형식)
- 예시 — 한국어 파이프라인의 경우: `src/labelers/ko/ner_prompts.py`

### 작업 내용

1. **프롬프트 구조 결정**: 현재 3종류 템플릿 존재

   | 템플릿 | 용도 | 코드 변수명 |
   |--------|------|------------|
   | SINGLE | 단일 문장 | `SINGLE_PROMPT_TEMPLATE` |
   | BATCH | 다중 문장 배치 | `BATCH_PROMPT_TEMPLATE` |
   | SYSTEM+USER | OpenAI 채팅 형식 | `SYSTEM_PROMPT` + `USER_PROMPT_TEMPLATE` |

2. **핵심 라벨링 규칙 작성**:

   예시 — 한국어 파이프라인의 경우 (`ner_prompts.py:50-57`):
   - 조사 제외 규칙 (은/는/이/가/을/를 등)
   - 접미사 처리 ("씨"/"님" 제외, "김모" → "김"만 추출)
   - 복합 개체명 묶기 ("지난19일" → DT)
   - 괄호 내 처리 규칙
   - 추출 제외 대상 (사건명, 작품명 등)
   - 출력 형식 제한 (JSON 배열만)
   - 빈 결과 처리 (`[]` 반환)

   > **언어별 주의사항**: 조사 처리, 접미사 규칙, 복합어 묶기 등 언어형태론 관련 규칙은 대상 언어의 특성에 따라 달라진다. 각 언어별 라벨링 규칙은 해당 언어의 언어학적 특성과 데이터셋 가이드라인을 기반으로 작성해야 한다.

3. **Few-shot 예시 설계**: 각 예시가 서로 다른 엣지 케이스를 커버하도록 구성

   예시 — 한국어 파이프라인의 경우 (`ner_prompts.py:59-79`):

   | 예시 | 커버하는 엣지 케이스 |
   |------|---------------------|
   | 1 | 일반명사 기관(경찰=OG), 접미사 제거, 괄호 내 숫자 |
   | 2 | 숫자+단위 묶기, 스포츠 용어 |
   | 3 | 붙어쓰기 날짜, 시간, 복합 지명 |
   | 4 | 복합 날짜, 시간 단독, 시대 표현 |
   | 5 | DT/TI 분리, 복수 LC |
   | 6 | 스포츠 맥락 국가→OG, 단위 없는 숫자 |
   | 7 | 괄호 안 날짜 분리, 아이돌 그룹→PS |

4. **출력 형식 지정**: JSON 배열 `[{"text": "...", "type": "..."}, ...]`

### 체크포인트

- [ ] 프롬프트에 모든 엔티티 타입의 정의가 포함되어 있는가
- [ ] Few-shot 예시가 주요 엣지 케이스를 커버하는가
- [ ] LLM에 프롬프트를 직접 보내서 유효한 JSON이 반환되는가 (수동 테스트)
- [ ] 3~5개 샘플에 대해 수동으로 결과를 검증했는가

```python
# 체크포인트 검증 코드: 프롬프트 수동 테스트 (예시 — 한국어 파이프라인의 경우)
from labelers.ko.ner_prompts import SINGLE_PROMPT_TEMPLATE
test_sentence = "삼성전자는 어제 서울에서 신제품을 발표했다."
prompt = SINGLE_PROMPT_TEMPLATE.format(sentence=test_sentence)
print(prompt)
# → LLM에 직접 전달하여 JSON 출력 확인
```

### 실패 패턴

| 증상 | 원인 | 조치 |
|------|------|------|
| 조사/어미가 엔티티에 포함됨 | 언어 형태소 제외 규칙 부족 | 해당 언어의 규칙 강화, 예시 추가 |
| 복합 개체명이 분리됨 | 묶기 규칙 부족 | 묶기 규칙 강화, 해당 패턴 예시 추가 |
| 사건명/작품명이 추출됨 | 제외 규칙 부족 | 제외 규칙에 예시 추가 |
| LLM이 JSON이 아닌 텍스트 출력 | 형식 지시 부족 | 형식 규칙 강화, "JSON 배열만 출력" 반복 명시 |
| 특정 패턴 일관성 없음 | 해당 패턴의 Few-shot 부재 | 해당 패턴을 커버하는 예시 추가 |

### 롤백 조건

이 단계로 돌아와야 하는 경우:
- Recall이 낮음 → 엔티티 누락 → 해당 패턴의 예시 보강
- Precision이 낮음 → 오탐 → 제외 규칙 강화
- 특정 엔티티 타입의 F1이 낮음 → 해당 타입의 규칙/예시 점검
- Step 7 반복 개선에서 프롬프트 수정이 필요하다고 판단될 때

## 6. Step 4: LLM 선정 및 설정

### 입력

- Step 3에서 설계한 프롬프트 템플릿
- 사용 가능한 LLM 백엔드 목록

### 출력

- LLM 인스턴스 설정 (모델명, temperature, JSON mode, 백엔드)
- 라벨러 클래스 인스턴스

### 작업 내용

1. **백엔드 선택**: 3개 백엔드 중 선택

   예시 — 한국어 파이프라인의 경우:

- [ ] `temperature=0`으로 동일 입력에 동일 출력이 나오는가

- [ ] thinking 토큰 없이 순수 JSON만 응답에 포함되는가
- [ ] 5개 샘플에 대해 라벨러 호출이 정상 동작하는가

# 체크포인트 검증 코드 (예시 — 한국어 파이프라인의 경우)

- 처리 속도가 요구사항을 충족하지 못할 때

## 7. Step 5: 파싱 및 후처리

### 입력

- Step 4의 LLM 인스턴스로부터 받은 JSON 응답 문자열

### 출력

- `label_spans()` 경로: `List[Dict]` — `[{"text": "경찰", "type": "OG"}, ...]`
- `label()` 경로: `NERRecord` — BIO 태그 리스트 `["B-OG", "I-OG", "O", ...]`

### 작업 내용

1. **JSON 파싱 구현**: 두 가지 파싱 경로
   - **인라인 파싱** (예: `vllm_ner_labeler.py`): `json.loads()` + 다양한 형태 처리 (list, dict, 래퍼)
   - **공통 파싱** (`labeler_base.py:10-34`): `<think>` 태그 제거, markdown fence 내 JSON 추출 등

2. **배치 실패 폴백**: 배치 파싱 실패 시 개별 문장 단위 재시도
   ```python
   # 예시 — 한국어 파이프라인의 경우 (vllm_ner_labeler.py)
   except (json.JSONDecodeError, Exception) as e:
       return [self._call_llm(s) for s in sentences]  # 개별 폴백
   ```

3. **spans → BIO 변환**: 토큰 리스트에서 span을 BIO 태그로 매핑 (2단계 매칭 전략)
   - 1단계 — Exact match: 토큰 리스트에서 span 토큰의 연속 일치
   - 2단계 — Substring match: 형태소 결합 등으로 exact match 실패 시 부분 일치

   > **언어별 주의사항**: BIO 변환의 매칭 전략은 언어의 토큰화 방식에 따라 달라진다. 예를 들어 한국어(음절 단위)의 경우 조사 부착 토큰을 위한 substring match가 필요하다 (`spans_to_syllable_bio()`, `tag_aligner.py:222-296`). 다른 언어는 해당 언어의 토큰화 방식에 맞는 매칭 전략을 구현해야 한다.

4. **태그 정규화**: `normalize_tag()` (`tag_aligner.py:44-59`)
   - 예시 — 한국어: `PER→PS`, `LOC→LC`, `ORG→OG`, `DATE→DT`, `TIME→TI`, `QUANTITY→QT`

### 체크포인트

- [ ] 유효한 JSON 응답이 올바르게 파싱되는가
- [ ] 비표준 형식 (단일 객체, 래퍼 dict)도 처리되는가
- [ ] `<think>` 태그, markdown fence가 포함된 응답도 파싱되는가
- [ ] 배치 실패 시 개별 폴백이 동작하는가
- [ ] spans → BIO 변환에서 대상 언어의 토큰 경계가 올바르게 매칭되는가
- [ ] 태그 정규화가 모든 변형을 커버하는가

```python
# 체크포인트 검증 코드: spans→BIO 변환 확인 (예시 — 한국어 파이프라인의 경우)
tokens = ["삼", "성", "전", "자", "는", " ", "어", "제"]
spans = [{"text": "삼성전자", "type": "OG"}, {"text": "어제", "type": "DT"}]
bio = labeler._spans_to_bio(tokens, spans)
print(list(zip(tokens, bio)))
# 기대: [("삼","B-OG"), ("성","I-OG"), ("전","I-OG"), ("자","I-OG"), ("는","O"), (" ","O"), ("어","B-DT"), ("제","I-DT")]
```

### 실패 패턴

| 증상 | 원인 | 조치 |
|------|------|------|
| `json.JSONDecodeError` 빈번 | LLM이 비유효 JSON 출력 | Step 4 (JSON mode 설정) 또는 파싱 폴백 강화 |
| spans는 맞지만 BIO가 틀림 | span→BIO 매칭 실패 | 매칭 전략 확인 (exact → substring 2단계) |
| 형태소/조사가 엔티티에 포함된 BIO | LLM이 형태소 포함 span 출력 | Step 3 (프롬프트 규칙) 형태소 제외 규칙 강화 |
| 빈 결과가 많음 | 파싱 에러로 빈 리스트 반환 | 에러 로깅 추가, 파싱 로직 디버깅 |

### 롤백 조건

이 단계로 돌아와야 하는 경우:
- Step 6 평가에서 seqeval과 Span Match 사이에 큰 괴리가 있을 때 (BIO 변환 문제)
- 파싱 실패율이 높을 때 (Step 4의 모델/설정 변경이 선행될 수도 있음)
- 특정 패턴의 span이 BIO로 올바르게 변환되지 않을 때

## 8. Step 6: 반복 개선

### 입력

- 평가 결과 (메트릭 리포트 — 평가 방법은 별도 재설계 중)
- 에러 분석 결과

### 출력

- 개선된 프롬프트/설정/파싱 로직
- 개선 전후 메트릭 비교

### 작업 내용

1. **에러 분석**: 평가 결과에서 어떤 유형의 오류가 많은지 분류
   - False Negative (누락): 어떤 엔티티 타입이 빠지는가
   - False Positive (오탐): 어떤 패턴이 잘못 추출되는가
   - Type Confusion: 어떤 태그 쌍이 혼동되는가

2. **원인 파악 및 해당 단계로 롤백**: 아래 [롤백 결정 트리](#10-실패-시-롤백-결정-트리) 참조

3. **변경 적용 후 재평가**: 변경 전후 메트릭을 비교하여 개선 여부 확인

4. **반복 종료 조건**:
   - 목표 F1 달성
   - 추가 개선의 비용 대비 효과가 미미
   - 에러가 gold 데이터의 노이즈에 기인

### 체크포인트

- [ ] 에러 분석 결과가 명확한 원인을 가리키는가
- [ ] 변경이 해당 문제만 해결하고 다른 부분에 부정적 영향을 주지 않는가 (회귀 확인)
- [ ] 변경 전후 메트릭 비교가 기록되어 있는가

### 실패 패턴

| 증상 | 원인 | 조치 |
|------|------|------|
| 한 문제를 고치면 다른 문제 발생 | 프롬프트 규칙 간 충돌 | 규칙 우선순위 정리, 예시로 명확화 |
| 개선이 정체됨 | 모델 능력 한계 | Step 4 (더 큰 모델) 또는 Step 2 (태그 정의 단순화) |
| 특정 도메인만 성능 저조 | 학습 데이터 편향 | Step 3 (해당 도메인 예시 추가) |

## 9. 실패 시 롤백 결정 트리

평가 결과가 기대에 미치지 못할 때, 아래 결정 트리를 따라 어느 단계로 돌아갈지 판단한다.

### 트리 1: F1이 낮을 때

```
F1이 전체적으로 낮음
    │
    ├── Span Match exact가 낮은가?
    │   ├── YES → 어떤 메트릭이 낮은가?
    │   │   ├── Precision 낮음 (오탐 많음)
    │   │   │   ├── 특정 패턴이 반복적으로 오탐? → Step 3: 해당 패턴 제외 규칙 추가
    │   │   │   └── 전반적 오탐? → Step 3: 프롬프트 규칙 전체 강화
    │   │   │
    │   │   └── Recall 낮음 (누락 많음)
    │   │       ├── 특정 엔티티 타입만 누락? → Step 3: 해당 타입 예시 보강
    │   │       ├── 긴 문장에서 누락 증가? → Step 5: 배치 크기 축소 또는 문장 분리 조정
    │   │       └── 전반적 누락? → Step 4: 모델 변경 또는 Step 3: Few-shot 예시 추가
    │   │
    │   └── NO (Span Match는 양호, seqeval만 낮음)
    │       └── → Step 5: spans→BIO 변환 로직 점검
    │
    └── 모든 메트릭이 0에 가까운가?
        ├── JSON 파싱 에러 로그 확인
        │   ├── 파싱 에러 다수 → Step 4: JSON mode 설정 또는 Step 5: 파싱 로직
        │   └── 파싱은 정상, 빈 결과 → Step 3: 프롬프트가 올바르게 전달되는지 확인
        │
        └── 데이터 로딩 확인
            └── gold 데이터 이상 → Step 1: 데이터셋 준비 재점검
```

### 트리 2: JSON 파싱 실패가 많을 때

```
JSON 파싱 실패율 높음
    │
    ├── <think> 태그가 응답에 포함?
    │   └── → Step 4: think=False 설정 확인, 또는 Step 5: <think> 제거 로직 추가
    │
    ├── JSON이 아닌 자연어 응답?
    │   └── → Step 4: format="json" (JSON mode) 설정 확인, 모델이 이를 지원하는지 확인
    │
    ├── 배치 응답에서만 실패?
    │   ├── 배치 크기 축소 시도 → Step 5: batch_size 조정
    │   └── BATCH 프롬프트 형식 문제 → Step 3: BATCH_PROMPT_TEMPLATE 수정
    │
    └── 간헐적 실패?
        └── → Step 5: 폴백 로직 강화 (배치 실패 → 개별 재시도)
```

### 트리 3: 특정 엔티티 타입 성능 저조

```
특정 엔티티 타입만 F1 낮음
    │
    ├── 해당 타입의 정의가 모호한가?
    │   └── → Step 2: 엔티티 정의 구체화 (경계 사례 명확화)
    │
    ├── 해당 타입의 Few-shot 예시가 부족한가?
    │   └── → Step 3: 해당 타입을 포함하는 예시 추가
    │
    ├── 해당 타입이 다른 타입과 혼동되는가?
    │   └── → Step 3: 두 타입의 구분 규칙을 프롬프트에 명시
    │       (예: "국가명이 스포츠 맥락에서 나오면 OG, 지리 맥락이면 LC")
    │
    └── gold 데이터에서 해당 타입의 어노테이션이 일관적인가?
        └── → Step 1: gold 데이터 품질 점검
```

### 트리 4: Precision vs Recall 불균형

```
Precision과 Recall 차이가 큼
    │
    ├── Precision ≫ Recall (보수적 추출)
    │   ├── 프롬프트가 너무 제한적 → Step 3: 제외 규칙 완화, 예시 다양화
    │   └── 배치 처리에서 누락 → Step 5: batch_size 축소
    │
    └── Recall ≫ Precision (과다 추출)
        ├── 프롬프트 제외 규칙 부족 → Step 3: 제외 규칙 강화
        │   (사건명, 작품명, 일반명사 등)
        └── 후처리 필터 부재 → Step 5: 후처리에서 오탐 필터 추가
```

### 빠른 참조 표

| 증상 | 1차 점검 | 롤백 대상 |
|------|----------|-----------|
| 전체 F1 낮음 | Precision/Recall 분석 | Step 3 (프롬프트) |
| 특정 엔티티 F1 낮음 | 해당 타입 에러 패턴 | Step 2 (정의) 또는 Step 3 (규칙/예시) |
| Recall 낮음 (누락) | 누락되는 패턴 확인 | Step 3 (예시 보강) 또는 Step 5 (배치 크기) |
| Precision 낮음 (오탐) | 오탐 패턴 확인 | Step 3 (제외 규칙) 또는 Step 5 (후처리 필터) |
| JSON 파싱 실패 | 에러 로그 확인 | Step 4 (모델/설정) 또는 Step 5 (파싱 로직) |
| Span Match ↔ seqeval 괴리 | BIO 변환 검증 | Step 5 (spans→BIO 변환) |
| 처리 속도 부족 | 모델 크기/배치 크기 | Step 4 (모델) 또는 Step 5 (배치) |
| gold 데이터 의심 | 샘플 수동 검증 | Step 1 (데이터셋) |
