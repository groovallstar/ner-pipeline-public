## 1. LLM 라벨링 검증 시 토큰 단위의 무관성

### 1.1 결론

LLM 라벨링 검증에서는 **Gold 데이터의 토큰 단위(음절/어절/형태소)가 본질적으로 중요하지 않다**. 현재 `src/labelers/tag_aligner.py`는 이미 양쪽(음절/어절)을 모두 처리하도록 구현되어 있다.

### 1.2 왜 span 형식인가 (프롬프트 설계 선택)

LLM이 span 리스트를 출력하는 것은 LLM의 본질적 특성이 아니라 **프롬프트가 그렇게 요청하도록 설계되었기 때문**이다. `src/labelers/ko/ner_prompts.py`의 `SINGLE_PROMPT_TEMPLATE`은 다음 세 지점에서 형식을 고정한다.

- `src/labelers/ko/ner_prompts.py:15` — `"텍스트에서 개체명을 찾아 JSON 배열로만 반환하세요."`
- `src/labelers/ko/ner_prompts.py:56` — `"JSON 배열만 출력, 다른 설명 금지"`
- `src/labelers/ko/ner_prompts.py:60-79` — 8개 few-shot 예시 전부 `[{"text": ..., "type": ...}]` 형식으로 제시

LLM은 이 few-shot 패턴을 모방(in-context learning)하여 같은 JSON span 구조로 응답한다. BIO가 아니라 span을 요청한 설계 근거는 다음 4가지이다.

1. **토큰화 독립성** — BIO를 요청하려면 먼저 "어떤 토큰 단위로 쪼갤지"를 합의해야 한다. LLM은 음절/어절/형태소 중 무엇으로 쪼갤지 불안정하고, gold 토큰과의 정렬도 어렵다. Span은 "원문의 어느 부분이 엔티티인가"만 답하므로 토큰화 단위 자체가 필요 없다.

2. **출력 토큰 효율** — 긴 문장의 모든 토큰에 BIO 태그를 붙이면 출력 토큰 수가 입력 길이와 비례해 커진다. Span은 엔티티 개수에만 비례하므로 출력이 훨씬 짧고 추론 비용·지연이 낮다.

3. **파싱 안정성** — JSON 배열은 파싱 실패 시 즉시 감지되고 재시도·복구가 가능하다. BIO 열은 토큰 수 불일치, `I-` 태그 누락·타입 드리프트 같은 조용한 정렬 오류가 발생하기 쉽다.

4. **자연스러운 출력 패턴** — 대형 LLM은 "이름 있는 것들을 뽑아달라"는 자연어 task에 span 리스트로 답하는 패턴에 이미 훈련되어 있어, BIO 열 출력보다 오류율이 낮고 few-shot만으로도 형식이 안정적으로 재현된다.

### 1.3 현재 코드가 이미 지원하는 증거

`src/labelers/tag_aligner.py:94-130` 의 `extract_spans_from_bio`:

```python

    has_space_tokens = any(t.strip() == "" for t in tokens)
```

- KLUE(음절 + 공백 토큰) → `joiner=""` → `['대','한','민','국']` → `"대한민국"`
- WikiANN(어절) → `joiner=" "` → `['대한민국']` → `"대한민국"`

동일 함수가 두 형식 모두 span으로 정확히 역변환한다.

## 2. 용어 정리 — 토큰화 단위 (음절 / 어절 / 형태소)

토큰화 단위는 **원문을 어떤 단위로 쪼개서 배열에 넣었는가**를 가리킨다. NER 데이터셋마다 선택이 다르며, BIO 태그가 붙는 축도 이 단위를 따른다.

### 2.1 세 가지 쪼개기 방식

원문: `"나는 서울특별시에 산다"`

| 단위 | 정의 | 결과 |
|------|------|------|
| **음절** | 한 글자 단위. 공백도 별도 토큰 | `['나','는',' ','서','울','특','별','시','에',' ','산','다']` |
| **어절** | 공백 기준 덩어리 | `['나는', '서울특별시에', '산다']` |
| **형태소** | 의미 최소 단위 (조사/어미 분리) | `['나','는','서울','특별시','에','살','ㄴ다']` |

### 2.2 각 단위별 BIO 태깅

같은 엔티티(`"서울특별시"`)라도 토큰화 단위에 따라 BIO 열이 다르게 붙는다.

**음절 단위 BIO (KLUE 방식)**
```
나(O) 는(O) (O) 서(B-LC) 울(I-LC) 특(I-LC) 별(I-LC) 시(I-LC) 에(O) ...
```

**어절 단위 BIO (WikiANN 방식)**
```
나는(O) 서울특별시에(B-LC) 산다(O)
```

어절 단위는 경계가 **어절 단위로 고정**되어 조사(`에`)까지 엔티티 영역에 포함된다. 음절 단위는 조사 위치에 정확히 경계를 잡을 수 있다. 형태소 단위는 조사가 이미 별도 토큰이므로 조사를 `O`로 처리하면 된다.

### 2.3 한 줄 요약

| 용어 | 의미 | 예시 |
|------|------|------|
| **음절** | 한 글자 단위 토큰 | `'서'`, `'울'` |
| **어절** | 공백으로 나뉜 덩어리 | `'서울특별시에'` |
| **형태소** | 의미 최소 단위 | `'서울'`, `'특별시'`, `'에'` |

## 3. 용어 정리 — Span

Span은 **원문에서 엔티티가 차지하는 범위와 타입**을 가리킨다. 토큰화 단위와는 독립된 축의 개념이다.

### 3.1 Span의 정의

원문: `"나는 서울특별시에 산다"`
Span: `{"text": "서울특별시", "type": "LC", "start": 3, "end": 8}`

- `text` — 원문에서 해당 범위의 문자열
- `type` — 엔티티 타입 (PS/LC/OG/DT/TI/QT 등)
- `start`, `end` — 원문 character offset (선택)

### 3.2 Span은 토큰화 단위와 독립적이다

BIO는 `토큰화 단위 × 엔티티 타입`의 교차이므로 같은 엔티티라도 데이터셋마다 표현이 다르지만, span은 "원문의 어느 범위"만 나타내므로 데이터셋 간 직접 비교가 가능하다.

```
음절 BIO  →  span [{"text":"서울특별시",   "type":"LC"}]
어절 BIO  →  span [{"text":"서울특별시에", "type":"LC"}]   ← 조사 포함
LLM 출력  →  span [{"text":"서울특별시",   "type":"LC"}]
```

BIO → span 역변환 함수: `src/labelers/tag_aligner.py:94` `extract_spans_from_bio`

### 3.3 한 줄 요약

| 용어 | 의미 | 예시 |
|------|------|------|
| **Span** | 원문에서 엔티티의 (시작, 끝, 타입) | `{"text":"서울특별시","type":"LC"}` |
| **Span 비교** | 토큰화 단위와 무관하게 P/R/F1 계산 가능 | gold span ∩ pred span |

## 4. 토큰 단위별 Span 추출 과정

`src/labelers/tag_aligner.py:94-130` `extract_spans_from_bio`는 공백 토큰 유무로 토큰 단위를 자동 감지한 뒤 BIO 태그를 하나의 span으로 병합한다. 세 가지 단위별로 단계를 구체화한다.

### 4.1 공통 알고리즘

```
1. tokens 안에 "순수 공백" 토큰이 있으면 syllable-level로 판정 → joiner = ""
   없으면 word/morph-level로 판정                              → joiner = " "
2. 태그를 순서대로 스캔하면서 B-<T>를 만나면 새 버퍼를 시작,
   같은 타입의 I-<T>가 이어지면 버퍼에 누적,
   O 혹은 다른 B-<T>를 만나면 지금까지의 버퍼를 joiner.join()하여 span으로 확정.
3. 각 span은 {"text": joiner.join(buffer), "type": 정규화된 타입} 형태.
```

핵심은 **joiner 선택 한 단계**로 음절/어절 양쪽이 동일 코드에서 처리된다는 점이다.

### 4.2 음절 단위 (KLUE) → Span

원문: `"영동고속도로 강릉"`

**입력 (tokens / tags)**
```
tokens = ['영','동','고','속','도','로',' ','강','릉']
tags   = ['B-LC','I-LC','I-LC','I-LC','I-LC','I-LC','O','B-LC','I-LC']
```

**단계별 처리**
```
1) ' ' (공백 토큰) 존재 → syllable-level → joiner = ""
2) 스캔:
   '영' B-LC  → 새 버퍼 시작: ['영'],        type=LC
   '동' I-LC  → 누적:        ['영','동']
   '고' I-LC  → 누적:        ['영','동','고']
   '속' I-LC  → 누적:        ['영','동','고','속']
   '도' I-LC  → 누적:        ['영','동','고','속','도']
   '로' I-LC  → 누적:        ['영','동','고','속','도','로']
   ' ' O      → 버퍼 확정 → "".join(...) = "영동고속도로"
   '강' B-LC  → 새 버퍼:     ['강'],        type=LC
   '릉' I-LC  → 누적:        ['강','릉']
   끝        → 버퍼 확정 → "강릉"
```

**출력**
```json
[{"text": "영동고속도로", "type": "LC"},
 {"text": "강릉",         "type": "LC"}]
```

### 4.3 어절 단위 (WikiANN) → Span

원문: `"현재 대한민국 K리그 챌린지의 서울 이랜드 FC에서"`

**입력 (tokens / tags)**
```
tokens = ['현재','대한민국','K리그','챌린지의','서울','이랜드','FC에서']
tags   = ['O','B-LOC','B-ORG','I-ORG','B-ORG','I-ORG','I-ORG']
```

**단계별 처리**
```
1) 공백 토큰 없음 → word-level → joiner = " "
2) 스캔:
   '현재'     O       → 무시
   '대한민국' B-LOC   → 새 버퍼: ['대한민국'],  type=LOC
   'K리그'    B-ORG   → 이전 버퍼 확정 → "대한민국"
                        새 버퍼:  ['K리그'],    type=ORG
   '챌린지의' I-ORG   → 누적:    ['K리그','챌린지의']
   '서울'     B-ORG   → 이전 버퍼 확정 → "K리그 챌린지의"
                        새 버퍼:  ['서울'],     type=ORG
   '이랜드'   I-ORG   → 누적:    ['서울','이랜드']
   'FC에서'   I-ORG   → 누적:    ['서울','이랜드','FC에서']
   끝        → 버퍼 확정 → "서울 이랜드 FC에서"
3) 타입 정규화: LOC→LC, ORG→OG
```

**출력**
```json
[{"text": "대한민국",            "type": "LC"},
 {"text": "K리그 챌린지의",       "type": "OG"},
 {"text": "서울 이랜드 FC에서",   "type": "OG"}]
```

> **주의:** `'챌린지의'`, `'FC에서'`처럼 조사가 어절 경계 내에 포함되어 있어 span이 조사까지 포함한다. KLUE 음절 단위와 달리 조사만 떼어낼 수 없는 구조적 한계이다.

### 4.4 형태소 단위 (KMOU) → Span

KMOU NER는 **비표준 BIO**를 사용한다: `I` 태그가 타입을 포함하지 않고 단독으로 등장하며, 직전 `B_<T>`의 타입을 상속한다.

원문(형태소 결합): `"이토 히로부미 안중근 만주 할빈"`

**입력 (tokens / tags)**
```
tokens = ['이토','히로부미','안중근','만주','할빈']
tags   = ['B_PS','I','B_PS','B_LC','B_LC']
```

**단계별 처리**
```
1) 공백 토큰 없음 → morph-level → joiner = " "
   (tag 구분자 '_' → '-'로 정규화하면 표준 BIO와 동일 처리 가능)
2) 스캔 (I는 현재 활성 타입 상속):
   '이토'     B_PS → 새 버퍼: ['이토'],        type=PS
   '히로부미' I    → 누적:    ['이토','히로부미']  (PS 상속)
   '안중근'   B_PS → 이전 버퍼 확정 → "이토 히로부미"
                    새 버퍼:  ['안중근'],      type=PS
   '만주'     B_LC → 이전 버퍼 확정 → "안중근"
                    새 버퍼:  ['만주'],        type=LC
   '할빈'     B_LC → 이전 버퍼 확정 → "만주"
                    새 버퍼:  ['할빈'],        type=LC
   끝        → 버퍼 확정 → "할빈"
3) 타입 정규화: PS→PS, LC→LC (KLUE와 동일)
```

**출력**
```json
[{"text": "이토 히로부미", "type": "PS"},
 {"text": "안중근",         "type": "PS"},
 {"text": "만주",           "type": "LC"},
 {"text": "할빈",           "type": "LC"}]
```

> **주의 1:** 형태소 단위는 원문 복원 시 형태소 간 공백이 원문에 없을 수 있어 `" "`로 join하면 원문과 차이가 날 수 있다. 엄격한 문자 오프셋 매칭이 필요하면 원문 텍스트와의 재정렬 단계가 추가로 필요하다.
> **주의 2:** KMOU의 `I` 단독 태그는 `extract_spans_from_bio`가 그대로 지원하지 않으므로, 로더에서 `I → I-<직전 B의 타입>`으로 치환하는 전처리가 선행되어야 한다.

### 4.5 세 단위의 비교 요약

| 단위 | joiner | span 경계 정확도 | 원문 재구성 | 전처리 필요 |
|------|--------|----------------|------------|-----------|
| 음절 (KLUE) | `""` | 글자 단위 정밀 (조사 분리 가능) | 원문 그대로 | 없음 |
| 어절 (WikiANN) | `" "` | 어절 단위 (조사 포함) | 공백 복원 | 없음 |
| 형태소 (KMOU) | `" "` | 형태소 단위 | 원문과 공백 불일치 가능 | `I` 태그 타입 상속 필요 |
