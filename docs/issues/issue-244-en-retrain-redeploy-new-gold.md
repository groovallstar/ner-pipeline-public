## 배경 (왜)

en 배포 패키지(`/data/ner/en/`)를 지금 코드와 함께 서비스할 수 없다. 학습 이후
정답이 두 번 바뀌었다.

- **2026-08-26 (#225)** 엔티티 밖 문장부호를 엔티티 안으로 라벨하던 결함을
  없앴다(en 전수 80,288건). 지금 체크포인트는 그 결함이 있는 라벨로 학습돼
  "엔티티 뒤 마침표는 엔티티 안" 이라고 배웠고, 새 정렬에서는 같은 예측이
  span 을 한 글자 늘려 strict 가 어긋난다.
- **2026-08-31 (#236·#239)** 원본 `FAC` 를 전량 `ORG` 로 태우던 것을 표면별
  판정으로 갈랐다. gold 가 `LOC` +274 · `ORG` −289 span 움직였고
  `dataset_fingerprint` 가 `39cb0f9e9c16f265` → `258166d6972c8144` 로 바뀌었다.

그래서 `certified/classifier/en/**` 의 수치는 전부 현행 코퍼스와 다른 gold 로
잰 것이고, 현행 gold 로 잰 값은 아직 하나도 없다. 낡은 결과가 저장소에 남아
있는 한 새 결과와 잘못 견줄 여지가 남는다.

부수적으로, 배포 패키지 `metrics.json` 의 `data_path` 가 #238 개명 이후 없는
파일(`data/ontonotes_en/pii_all.jsonl`)을 가리켜 `build_ner_prod.py` 재포장이
`dataset not found` 로 멈춘다. ko 는 `fad820b` 로 고쳤고 en 은 빠졌다.

## 목적

현행 gold 로 `roberta-base` 를 다시 학습해 새 baseline 을 세우고 그 체크포인트를
`/data/ner/en/` 으로 재출하한다. 낡은 자로 잰 원장과 모델 산출물은 남기지 않고
제거해, 잘못 견줄 대상 자체를 없앤다.

## 범위

**포함** — `roberta-base` 3-seed(42·43·44) 재학습(#215 와 같은 조건, gold 만
현행) · 배포 패키지 재포장 + `data_path` 정상화 · 옛 원장·옛 모델 산출물 제거 +
새 원장 승격

**제외**

- **`RULER_FIELDS` 에 정렬 세대 필드 추가** — #225 가 후속으로 남긴 항목이지만
  이 이슈에서 하지 않는다. 아래 §정렬 세대 필드를 안 만드는 이유.
- **백본 재선정** — #215 의 `roberta-base` 결론을 승계한다. FAC 재라벨이 옮긴
  것은 `LOC`↔`ORG` 289 span 이라 백본 순위를 뒤집을 축이 아니라고 보지만,
  **이 가정 자체는 이 이슈에서 검사하지 않는다.**
- 서버 `lang=en` 서빙 — `detect.py` 의 양성 감지 원칙이 선행 결정이다
- 코퍼스 재생성 — PII 주입은 LLM 산출이라 되돌릴 수 없다

**이 이슈는 기준 파일(`gate_core.py` 의 `RULER_PATHS`·`RULER_DIRS`)을 하나도
건드리지 않는다.** 커밋마다 사람 승인 + 반박자 PASS 를 받는 2단계가 걸리지
않는다.

## 정렬 세대 필드를 안 만드는 이유

#225 의 후속 항목이 "재학습 이슈의 수락 기준에 정렬 리비전 필드를
`RULER_FIELDS` 에 추가하는 항목을 넣어야 한다" 였다. 검토했고 **하지 않기로
했다.** 판단 근거를 남긴다.

### 막으려는 것

`_trim_offset` 같은 정렬 코드가 바뀌면 같은 문장·같은 정답인데 모델이 학습하는
BIO 라벨이 달라진다. #225 의 예로, `He works at Apple.` 의 마지막 토큰 `.` 은
수정 전 `I-ORG`, 수정 후 `O` 였다. 그러면 수정 전 학습된 모델을 수정 후 코드로
채점할 때 점수가 떨어지는데, 그건 모델이 나빠진 게 아니라 재는 자가 바뀐
것이다.

`RULER_FIELDS` 는 이 변화를 못 본다. `data_fingerprint` 는 gold **파일**의
해시라 파일이 안 바뀌면 그대로이고, `offset_trim` 은 수정 전후 모두 `True` 인
데다 판정에 안 쓰인다.

### 두 갈래와 택한 쪽

| 길 | 방법 | 이 이슈의 선택 |
|---|---|---|
| 잘못 견줄 때 잡아낸다 | 자에 칸을 더하고 그 칸이 실제로 움직이는지 검사 | ✕ |
| 낡은 결과를 안 남긴다 | 자가 바뀌면 그 자로 잰 원장을 제거 | ○ |

첫 번째를 설계하다 보니 딸리는 검사가 계속 늘었다 — 값이 안 움직임을 고정하는
골든, 움직여야 할 때 움직이는지 보는 민감도, `--legacy-no-offset-trim` 우회를
막는 검사, 세 토크나이저 중 무엇을 고정할지. **원래 문제보다 장치가 커졌다.**

두 번째는 잘못 견줄 대상 자체를 없앤다. `certified/` 에 현행 자로 잰 것만
둔다는 규율 하나로 끝난다.

### 대신 포기한 것

**이건 기계 검사가 아니라 관행이다.** `results/` 의 휘발 산출물끼리 견주거나
문서의 옛 표를 눈으로 견주는 경우는 아무것도 안 막는다. 정렬 코드만 바뀐 두
실험을 나란히 놓는 일이 실제로 생기면 그때 별건으로 연다.

### 참고 — 검토했던 후보들

나중에 이 판단을 되짚을 때 쓰라고 남긴다. 정렬은 두 단계로 일어난다 — 토큰마다
원문의 글자 구간을 정하는 단계 1(세 갈래로 분기)과, 그 구간을 gold entity 와
대조해 BIO 를 붙이는 단계 2(`_bio_labels_from_offsets`, 셋 공통)다.

| 갈래 | 언제 타나 | `_trim_offset` |
|---|---|---|
| `_encode_vi` | fast 토크나이저 (en `roberta-base`·ko) | 부른다 |
| `_encode_phobert` | PhoBERT (vi 배포본) | 안 부른다 |
| `_encode_ja` | slow (ja 배포본) | 안 부른다 |

| 후보 | 값을 어디서 만드나 | 덮는 범위 | 대가 |
|---|---|---|---|
| 동작 해시 (토크나이저 없이) | 런타임 | `_trim_offset` + 단계 2 | ja·phobert 단계 1 미커버 |
| 동작 해시 (고정 토크나이저 셋) | 런타임 | 세 갈래 전부 | 학습마다 토크나이저 셋 의존 |
| 상수 + 대조 테스트 | 테스트 | 세 갈래 전부 | 테스트 skip 시 상수 무방비 |
| `data_utils.py` 파일 해시 | 런타임 (자기 해시) | 세 갈래 전부 | 리팩터·주석에도 값이 움직임 |

값을 run 자신의 토크나이저로 계산하는 안은 일찍 뺐다 — `RULER_FIELDS` 에
`model_name` 이 일부러 빠져 있어(백본 비교가 정상 용법) 토크나이저를 값에
접으면 백본 비교가 통째로 거부된다.

## 결정 로그 (append-only)

- **2026-08-31**: 재벤치 범위를 `roberta-base` 3-seed 로 정했다. 6종 × 3-seed
  전량 재벤치(런 18회 ≈ 17 GPU-h)는 백본 선택이 gold 변경에 안 흔들린다는
  것까지 증거로 남기지만, 재출하가 그만큼 늦어진다. 사람이 3-seed 를 골랐다.
- **2026-08-31**: 옛 원장을 남기지 않고 제거하기로 했다. 대신 제거 전에
  `docs/reports/english-ner-corpus-spec.md` 를 새로 쓰고
  `english-bert-classifier-benchmark.md` 에 gold 세대 표시를 넣어, 수치의 세대
  귀속이 원장 밖에 남게 했다. 새 문서에 F1 값을 복제하지 않은 것은 원장을 지운
  뒤 대조 없는 표가 하나 더 생기는 것을 막기 위해서다.
- **2026-08-31**: 정의-시점 반박자가 REJECT 를 냈고 기준을 5개에서 6개로 고쳤다.
  가장 큰 것은 **골든 테스트가 안정성만 증명한다**는 지적이었다 — 해시가 안
  움직임은 고정하지만 움직여야 할 때 움직이는지는 아무것도 안 봐서, 커버리지
  0 인 probe 가 가장 안정적인 해시를 낸다. 같은 라운드에서
  `--legacy-no-offset-trim` 우회, `backbone_summary --check` 가 지문을 대조
  안 함, 재학습이 원래 결함을 지웠는지 재는 기준 부재, 매달릴 출처 선언 여덟
  군데를 함께 받았다.
- **2026-08-31**: **정렬 세대 필드를 이 이슈에서 빼고 기준을 6개에서 4개로
  줄였다.** 반박자 지적을 반영할수록 검사가 검사를 부르며 장치가 원래 문제보다
  커졌다. 낡은 원장을 제거하면 잘못 견줄 대상 자체가 없어지므로, 탐지가 아니라
  제거로 푼다. 대가는 이 방어가 기계 검사가 아니라 관행이라는 것이며 위
  §정렬 세대 필드를 안 만드는 이유에 적었다. 이 결정으로 이 이슈는 기준 파일을
  하나도 안 건드리게 됐다.
- **2026-08-31**: 삭제 범위를 `certified/classifier/en/` 네 디렉토리 전부로
  정했다. `issue225-offset-audit`·`issue225-ruler-shift` 는 모델 성능이 아니라

## 남는 한계

- 원장을 지우면 세대 1·2 수치는 문서 표로만 남고 기계 대조 근거가 없어진다.
  이미 커밋된 표는 인용 대조 대상이 아니므로 게이트가 이 상태를 붙잡지 않는다.
- 정렬 코드만 바뀐 두 실험을 나란히 놓는 것은 여전히 기계가 안 막는다.
- 백본 재선정을 안 하므로 "`roberta-base` 가 현행 gold 에서도 최선" 은 이
  이슈가 증거를 대지 않는 가정으로 남는다.
- 3-seed 중 배포되는 하나만 지문이 대조된다(기준 3 의 상수). 나머지 둘은
  아무도 안 보므로 median 이 이론상 오염될 수 있다. 실현 경로가 `--data` 를
  일부러 딴 파일로 돌리는 것뿐이라 감수한다.

## 검증

네 기준 모두 통과했다. 수치의 정본은 새 원장이고, baseline 표는
`docs/reports/english-bert-classifier-benchmark.md` §현행 gold 의 `roberta-base`
baseline 에 있다.

### 기준 1 — 정렬이 더 잃지 않았다

현행 코퍼스 76,378행 · 엔티티 167,856 전수를 `roberta-base` 토크나이저로 감사했다.
경계 위반 라벨은 **0건**이고, gold 왕복 복원 실패는 **열 타입 전부 세대 2 와 같다.**

| 타입 | 세대 2 실패 | 세대 3 실패 | 세대 2 모수 | 세대 3 모수 |
|---|---:|---:|---:|---:|
| PER | 42 | 42 | 19,260 | 19,260 |
| LOC | 460 | 460 | 21,671 | 21,945 |
| ORG | 522 | 522 | 17,379 | 17,090 |
| PROD | 13 | 13 | 1,990 | 1,990 |
| EVT | 0 | 0 | 946 | 946 |
| DAT | 16 | 16 | 13,926 | 13,926 |
| EMAIL | 1 | 1 | 24,105 | 24,105 |
| PHONE | 0 | 0 | 23,115 | 23,115 |
| ID_NUM | 0 | 0 | 22,529 | 22,529 |
| CREDIT_CARD | 2 | 2 | 22,950 | 22,950 |
| **전체** | **1,056** | **1,056** | **167,871** | **167,856** |

**이 표가 이 문서에 있는 이유는 세대 2 열이 저장소의 다른 어디에도 안 남기
때문이다.** 원본이던 `certified/classifier/en/issue225-offset-audit/` 는 기준 4 가
지웠고, `docs/issues/issue-225-zero-length-span-boundary.md` 의 표는 건수가 아니라
비율을 소수 넷째 자리까지만 싣는다. 세대 3 열의 정본은 새 원장
(`certified/classifier/en/offset-audit/audit_corpus.json`)이다.

모수가 움직인 두 타입은 `FAC` 재라벨의 결과다 — `ORG` 는 289 를 잃고(`LOC` 로
274 이동 · 15 삭제) `LOC` 은 274 를 얻었으며, 그 수는 마이그레이션 원장
`fac_disk_migration_ledger.json` 의 `move`·`remove` 와 정확히 맞는다. 빠진 289 가
전부 복원에 성공하던 엔티티라 `ORG` **비율**만 0.969964 에서 0.969456 으로
내려갔는데, 같은 522 건 실패의 지분이 커진 것이지 정렬이 더 잃은 것이 아니다.
이 관찰이 기준 1 의 판정을 비율에서 건수로 바꾸게 했다(결정 로그).

배포 체크포인트를 test 7,637행에 재평가한 결과도 함께 승격했다
(`audit_deployed_ckpt.json`). strict overall F1 이 학습 경로·포장 경로·감사 경로
셋에서 모두 0.9301 로 같아, 감사 스크립트가 기존 평가 경로와 같은 답을 낸다.

### 기준 2 — 3-seed 가 현행 gold 로 돌았다

세 run 모두 `data_fingerprint = 258166d6972c8144` 단일값이고
(`median_summary.json` 의 `data_fingerprints` 가 원소 하나짜리 배열이다),
`backbone_summary --check` 가 세 run 의 시각 정합을 통과시켰다(gap 49~51초).
NER-5 strict micro-F1 median 은 리포트 표에 박았다. 세대 1 값과의 대소는
해석하지 않는다.

집행에 새 코드를 만들지 않았다. 코퍼스가 현행 세대라는 것은
`test_the_corpus_matches_the_after_fingerprints` 가 디스크 네 파일의 sha256 을
바이트 단위로 대조해 이미 보증한다.

### 기준 3 — 배포 패키지가 새 run 에서 나왔다

`build_ner_prod.py` 가 완주했다. 그 완주 자체가 `data_path` 가 살아 있다는
집행이다 — 스크립트가 그 경로를 열어 분할을 다시 유도하고 지문·크기를 대조하며,
죽은 경로였다면 `dataset not found` 로 멈춘다. 재유도한 분할이 run 과 일치했고
(`61104/7637/7637`) test 그룹 누출은 0 이다.

`test_en_deploy_package.py` 의 상수 넷은 출처를 코퍼스로 못 박아 docstring 에
남겼다 — 지문은 `dataset_fingerprint(load_jsonl('data/ontonotes_en/origin.jsonl'))`
직접 실행값, 분할 셋은 76,378 행을 선언 비율로 나눈 값이다. 새 run 의
`metrics.json` 에서 베끼지 않았다. `LEDGER` 경로는 새 원장의
`roberta-3seed/roberta_base_seed42/metrics.json` 으로 옮겼다.

배포본은 점수가 아니라 seed 로 골랐다 — `train_seed 42` 다. 결과적으로 그것이
median draw 이기도 하지만, 셋 중 최고를 고르면 배포 선택 자체가 seed 뽑기가 된다.

### 기준 4 — 세대 3 원장만 남았다

`certified/classifier/en/` 의 옛 네 디렉토리와 `results/classifier/en/` 의 옛
run 을 지우고 새 산출물을 승격했다. 매달린 `<!-- certified: -->` 선언 여덟
군데를 같은 커밋에서 지웠고, `tests/test_certified_declarations.py` 가 `docs/**`
전수를 훑어 남은 선언이 전부 원장의 실재 경로를 가리키는지 본다. 그 테스트는
선언을 하나도 못 찾는 상태(정규식이나 경로가 어긋난 경우)에서 조용히 통과하지
않도록 커버리지 0 을 먼저 막는다.

| 원장 경로 | 무엇 |
|---|---|
| `classifier/en/roberta-3seed/` | 3-seed run metric 셋 + `median_summary.json` |
| `classifier/en/offset-audit/` | 코퍼스 전수 정렬 감사 + 배포 체크포인트 재평가 |
