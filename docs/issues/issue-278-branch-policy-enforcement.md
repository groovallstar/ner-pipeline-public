# issue-278: 브랜치 접두사와 PR 대상의 기존 결정 적용 누락

- Issue: https://github.com/groovallstar/ner-pipeline/issues/278
- 작업 공간: `/work/git/ner-pipeline`
- 브랜치: `develop` (이번 작업에 대한 사용자 지정 예외)
- 상태: develop 작업 공간에 변경 반영 및 재검증·독립 리뷰 완료, 미커밋

## 배경

Codex가 기존 프로젝트의 `feat/` 브랜치 규칙과 `develop` 기준을 적용하지 않고 일반적인 Git 명명 관행과 직전 작업의 일회성 예외를 다음 작업에 적용했다. 사용자가 반복해서 바로잡아야 했으며, 문서·테스트 검증이 통과한 상태에서도 브랜치 메타데이터 오류는 걸러지지 않았다.

## 목적

작업 종류와 관계없이 `feat/` 접두사를 사용하고, 기본적으로 `develop`에서 분기하여 `develop` 대상 PR을 생성하도록 기존 결정을 실제 실행 절차에 연결한다. 개별 작업에서 승인된 예외가 이후 작업의 기본값으로 전파되지 않도록 한다.

## 현 상태와 확인된 증상

- PR #274의 브랜치가 `chore/remove-ko-en-eval-scripts`로 생성되었다. 이 PR의 `main` 머지는 사용자가 해당 작업에 대해 명시적으로 요청한 정상적인 예외였다.
- 다음 문서 작업에서 `docs/api-caller-guides` 브랜치를 `main` 기준으로 만들고 PR #275의 대상을 `main`으로 지정했다.
- PR #275의 커밋은 작업 브랜치에 있었으며, `main`에 직접 커밋하거나 머지한 것은 아니다. 사용자 정정 후 PR #275는 미머지 상태로 닫혔다.
- `develop`에서 문서 커밋만 옮겨 PR #276을 만들었고, 해당 PR은 `develop`에 머지되었다. 그러나 새 브랜치도 `docs/api-caller-guides-develop`이어서 `feat/` 규칙 위반은 남았다.
- 사용자가 기본 접두사는 작업 종류와 관계없이 `feat/`라고 다시 명시했다.
- 위 증상은 수정 전의 기록이다. 현재는 사용자 후속 요청에 따라 루트 지침을
  수정하고 선택 시나리오를 검증한다. 자동 검사 도구는 추가하지 않는다.

## 근거

- `docs/issues/README.md`의 이슈 문서 템플릿은 `feat/issue-{N}-{슬러그}`를 사용한다.
- `docs/issues/issue-271-ner-api-invariants.md` 결정 로그에는 사용자 정정에 따라 `fix/`를 “기본 규칙인 `feat/`”로 변경한 기록이 있다.
- 수정 전 루트 `AGENTS.md`는 런타임 변경을 main 외 브랜치에서 진행하도록 규정하지만, `feat/` 접두사와 `develop` 분기·PR 대상을 직접 명시하지 않았다.
- 같은 파일의 `feat`, `fix`, `docs`, `chore` 규칙은 커밋 제목의 type에 관한 것이며, 브랜치 접두사의 허용 목록이 아니다.
- 원격 사실 확인: https://github.com/groovallstar/ner-pipeline/pull/274 · https://github.com/groovallstar/ner-pipeline/pull/275 · https://github.com/groovallstar/ner-pipeline/pull/276

## 원인 분석

아래는 대화와 실행 기록에 근거한 원인 분석이며, 모델 내부의 처리 과정을 직접 관측한 설명은 아니다.

1. **일반 관행의 무근거 적용:** 문서에는 `docs/`, 정리에는 `chore/`를 사용하는 관행을 프로젝트 결정과 대조하지 않고 적용했다. 커밋 종류와 브랜치 접두사를 구분하지 못했다.
2. **예외 범위의 확대:** PR #274에 한정된 `main` 머지 요청을 다음 PR의 분기 기준과 대상으로 확대했다.
3. **확인한 결정의 적용 누락:** 같은 세션에서 `feat/` 정정 기록을 읽었지만 이후 브랜치 생성에 반영하지 않았다. 단순히 기록을 찾지 못한 문제로만 설명할 수 없다.
4. **실행 직전 검증 누락:** 테스트·문서 diff·코드 리뷰는 수행했지만 브랜치 생성과 PR 작성 직전에 접두사, 분기 기준, PR 대상을 기존 결정과 대조하지 않았다.
5. **지침 배치의 기여 요인:** 규칙이 루트 지침보다 템플릿과 과거 결정 로그에 분산되어 있다. 이는 재발 가능성을 높이지만 이미 확인한 사용자 결정을 어긴 행동을 정당화하지 않는다.

## 범위와 후속 방향

후속 요청인 “이슈 278 진행”에 따라 아래 재발 방지 지침 수정을 진행한다.
선택 시나리오를 실제 로컬 Git 저장소에서 확인하며, 자동 검사 도구의 도입은
이번 변경에 포함하지 않는다.

- 루트 지침에서 브랜치 접두사와 커밋 type을 구분하고, `develop` 분기·PR 대상의 기본값을 명시한다.
- 브랜치 생성 전 접두사와 기준 브랜치를, PR 생성 전 대상 브랜치와 포함 커밋을 확인하도록 절차를 정한다.
- 예외는 사용자가 명시한 작업에 한정하고 이후 작업에 자동 승계하지 않는다.
- 기존 머지 이력 변경, 원격 브랜치 강제 갱신, 테스트·서버 기능 변경은 이 이슈의 해결에 포함하지 않는다.

## 성공 기준

- [x] 별도 사용자 지정이 없으면 기능·버그 수정·문서·정리 작업 모두 `feat/` 브랜치를 사용하며 커밋 type과 구분된다.
- [x] 별도 사용자 지정이 없으면 `develop`에서 분기하고 PR 대상도 `develop`으로 설정한다.
- [x] 특정 작업에서 `main` 머지를 승인받아도 다음 작업은 다시 기본 규칙을 따른다.
- [x] 브랜치/PR 생성 전에 이름·기준·대상·포함 커밋을 확인하는 절차가 지침에 명시된다.
- [x] 지침 검증은 문구 존재 검사만으로 완료하지 않고, 문서 작업·정리 작업·일회성 main 예외 다음 작업의 시나리오에서 실제 선택 결과를 확인한다.

- [x] worktree 분리는 사용자가 명시적으로 요청한 경우에만 수행하고, 이번 작업은 기존 `develop` 작업 공간에서 진행한다.

### 재발 방지 검증

`python3 - <<'PY'`로 임시 저장소를 만들고 `main`의 초기 커밋 뒤에
`develop` 전용 커밋을 추가했다. 아래 값은 작업자가 지침을 적용해 직접 선택한
값이며 정책 판정 함수를 구현한 자동 테스트는 아니다. 각 선택을
`git switch -c <브랜치> develop`로 실행하여 실제 브랜치 이름과 시작 SHA가
일치하는지 검사했다. 커밋 type별 빈 커밋을 만든 뒤
`git log --format=%s <대상>..HEAD`의 포함 커밋도 대조했다.

| 시나리오 | 실제 생성 브랜치 | 커밋 type | 분기 기준 | 선택한 PR 대상 | 결과 |
|---|---|---|---|---|---|
| 기능 | `feat/add-feature` | `feat` | `develop` | `develop` | 해당 작업 1커밋만 포함했다. |
| 버그 수정 | `feat/correct-behavior` | `fix` | `develop` | `develop` | 해당 작업 1커밋만 포함했다. |
| 문서 | `feat/update-guide` | `docs` | `develop` | `develop` | 해당 작업 1커밋만 포함했다. |
| 정리 | `feat/remove-unused` | `chore` | `develop` | `develop` | 해당 작업 1커밋만 포함했다. |
| 이번 작업만 main 머지 승인 | `feat/approved-main-merge` | `chore` | `develop` | `main` | 관계없는 `develop-only` 커밋을 발견하여 PR 생성 보류를 선택했다. |
| 위 예외 다음 문서 작업 | `feat/next-guide` | `docs` | `develop` | `develop` | 예외를 승계하지 않았으며 해당 작업 1커밋만 포함했다. |

- 결과: 6개 로컬 Git 시나리오가 모두 통과했다. 기본 작업의 PR 명령은
  `gh pr create --base develop --head <실제 브랜치>`로 구성했으며 실행하지 않았다.
- 초기 `python` 실행은 명령을 찾지 못해 실패했다. `python3`로 다시 실행하여
  위 결과를 얻었다. 초기 실행 실패를 검사 대상의 결함으로 집계하지 않았다.
- 최초 작업에서는 fetch한 `origin/develop`에서 `feat/` 작업 브랜치를 만들었으며
  기존 작업 공간의 미커밋 변경을 가져오지 않았다. 기존 이슈 문서만 복사하여 갱신했다.
- `git diff --check`는 통과했다. 문서만 변경하므로 pytest와 Ruff는 실행하지 않았다.
- 한계: 시나리오는 이번 작업자의 선택과 로컬 Git 결과를 확인한다. 향후 모든
  에이전트의 규칙 준수나 원격 PR 생성 후 head/base 확인까지 보장하지 않는다.
  실제 PR 생성, 원격 이슈 갱신, 커밋·푸시는 수행하지 않았다.
- 이전 변경의 완료 전 리뷰: Superpowers `requesting-code-review` 절차의 독립 리뷰
  서브에이전트가 최종 미커밋 diff와 이슈 문서 전체를 검토했다. Critical,
  Important, Minor 지적은 모두 없었으며 수정 요청도 없었다. 리뷰어는
  시나리오를 독립 재실행하지 않았고 원격 PR 생성 경로는 미검증으로 남겼다.

### 사용자 정정 반영 검증

  `develop` 브랜치와 `/work/git/ner-pipeline` 작업 경로 유지를 확인했다.

  검사 결과를 사용한다. 원격 PR 경로는 계속 미검증 상태이다.
