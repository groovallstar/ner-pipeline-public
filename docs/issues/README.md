# docs/issues/ — 이슈 문서 보관소

GitHub Issues의 계획·결과 스냅샷을 누적 보관하는 디렉토리다. 실시간 협의·승인 기록은 GitHub Issue 본문·댓글이 **단일 출처(single source of truth)**이고, 이 디렉토리는 기능 설계·구현 히스토리를 **영구 보존**하는 용도로만 쓴다.

운영 전반 규칙은 프로젝트 루트 `CLAUDE.md` → "이슈 관리" 섹션 참조.

## 디렉토리 구조

```
docs/issues/
├── README.md                                # 이 파일 (규칙·템플릿)
└── issue-{번호}-{슬러그}.md                  # 이슈별 계획+구현 통합 문서
```

- `{번호}`: GitHub Issue 번호 (gh가 부여한 자동 채번 값)
- `{슬러그}`: kebab-case 영문 요약 — 브랜치 슬러그와 동일하게 맞춘다. 예) `vi-crawler`, `ja-pii-verify`, `span-evaluator-fix`
- 파일은 이슈별 **단일 .md**로 관리한다. 계획과 구현 결과를 한 파일 안에 상하로 배치하고, 디렉토리·하위 파일은 만들지 않는다.
- **파일명에는 날짜를 넣지 않는다.** 이슈 번호가 영구 식별자이고, 머지·종결 시점은 GitHub Issue/PR 메타데이터와 git 이력에 남는다.

## 작성·커밋 시점

| 단계 | 동작 | 커밋 여부 |
|---|---|---|
| 3단계 (계획 승인 직후) | 계획 섹션을 로컬에 기록 | **커밋하지 않음** |
| 4단계 (구현 중) | 필요 시 plan 수정 + 결정 로그 한 줄 추가 | 커밋하지 않음 |
| 5단계 (PR 직전) | §변경 요약·검증·관련 커밋 채움 | 양쪽이 정상 작성됐는지 확인 후 **이때 최초 커밋** |

- 이슈 문서는 "계획 단계"에서는 커밋하지 않고 사용자가 로컬에서 직접 읽어가며 진행한다.
- 구현이 끝난 뒤 같은 파일에 결과 섹션을 추가하고, 전체 흐름이 정합적인지 검토한 뒤 한 번에 커밋한다.
- 머지 이후 plan 이 stale 해지면 `docs(issues):` 접두사로 후속 커밋(`refs #N`)으로 정리한다.

## 문서 구조 — state-first 원칙

이슈 doc 은 **plan 이 아니라 state** 를 우선 기록한다. plan 은 자주 바뀌고 stale 되지만 state·decision 은 누적되어도 유효하다. 다음 3-layer 분리:

| Layer | 성격 | 변경 빈도 | 위치 |
|---|---|---|---|
| **Goal** (이슈) | 왜 필요한가 + 측정 가능한 결과 | 거의 안 바뀜 | §배경·목적·성공 기준 |
| **Path** (plan) | 현재 최선의 접근 | 자주 바뀜 (정상) | §구현 단계 (가변) |
| **Decision log** | 왜 방향이 바뀌었나 | append-only | §결정 로그 |

핵심 규칙:
- plan 이 흔들릴 때마다 §결정 로그 에 한 줄 추가 (`YYYY-MM-DD: 사유`). plan 은 그대로 수정, decision 은 절대 수정·삭제 안 함.
- state (fact) 와 plan 을 시각적으로 분리해서 다음 세션이 *fact + open question* 만 읽고 시작 가능하게 한다.
- §"다음 세션 진입 가이드" 같은 cold-start 섹션은 만들지 않는다. 다음 세션은 §"현 상태 (fact)" + §"미해결 질문" 만 읽고 진입한다.

## 반박자 라운드 기록

반박자 지적으로 방향이 바뀌었으면 §결정 로그에 한 줄 남긴다. **라운드 수와 총계는 세지 않는다.**

| 적는다 | 안 적는다 |
|---|---|
| "반박자가 이걸 지적해서 이렇게 바꿨다" | 지금까지 돈 라운드 수 (`열다섯 라운드 중`) |
| 그 라운드가 무엇을 잡았는지 | 유형별 집계·총계 (`어긋남이 넷`) |
| PASS 라운드가 남긴 비차단 지적 | 라운드를 빠짐없이 담은 표 |

판정 이력의 정본은 `.omc/state/refuter/` 다. 라운드별 기록은 완결성을 주장하지 않으므로 하나가 비어도 결함이 아니다.

**PASS 뒤에는 문서를 고치지 않는다.** 반박자 PASS 와 사람 승인은 그 시점 diff 지문에 묶여, 뒤에 무엇을 고치든 함께 무효가 된다. 순서는 `문서 완성 → 반박자 → PASS → 사람 승인 → 커밋` 이다.

## 이슈 분할 규칙

- **한 이슈 = 한 goal** — 측정 가능한 단일 outcome. 다른 메커니즘이 섞이면 분할.
- **분할 vs 합침**: 다른 메커니즘은 분할, sequential discovery 는 같은 이슈 결정 로그에 누적. 무조건 잘게 쪼개지 않는다 (이슈 overhead 비용).

## 이슈 md 템플릿

섹션은 **tier**로 구분한다. 모든 섹션을 다 쓸 필요는 없다 — **필수**만 강제, 나머지는 작업 성격에 맞게 취사한다.

**섹션 이름은 작업 성격(감사·진단·측정·feature)에 맞게 개명해도 된다 — layer(개념)만 보존하면 된다.** 정규 이름은 출발점일 뿐 강제가 아니다. 자주 쓰는 개명:

- `구현 단계` → `계획`
- `변경 요약` → `구현 결과`
- `결정 로그` → `결정` (단 append-only 성격은 유지)
- `성공 기준` → §검증의 AC(acceptance criteria) 항목으로 흡수
- `배경` → `동기` · `문제` · `근본 원인` · `배경/가설` (작업 성격이 진단·재감사면 이쪽이 자연스럽다. **§목적 안에 흡수하지는 않는다** — 아래 필수 tier 참조)

| Tier | 의미 | 섹션 |
|---|---|---|
| **필수** | 모든 이슈 doc에 반드시 | **배경(왜)** · 목적 · 성공 기준 · 검증 |
| **불변식** | plan이 흔들리면 한 줄 추가 (append-only, 수정·삭제 금지) | 결정 로그 |
| **권장** | 작업 성격상 해당되면 | 범위 · 현 상태(fact) · 구현 단계 |
| **옵션** | 필요할 때만 | 위험·의존성 · 미해결 질문 · 변경 요약 · 관련 커밋 · 후속 작업 |

**§배경과 §목적은 붙여 쓰지 않는다.** 목적은 "metric 으로 표현한 도달 상태"라 *어디로 가나*만 말하고, 왜 지금 거기로 가야 하는지는 못 담는다. 둘을 한 섹션에 합치면 측정 가능한 문장이 왜를 밀어내 — 실제로 그렇게 쓰인 옛 doc 이 여럿 있다 — 나중에 범위가 흔들릴 때 무엇을 지켜야 하는지, 끝난 뒤 그 작업이 문제를 실제로 없앴는지 판정할 기준이 사라진다. 그래서 왜를 별도 필수 섹션으로 앞에 둔다. **배경이 한 줄도 안 써지면 갈래부터 잘못 잡았을 수 있다** — 되짚을 문제가 없는 작업이면 애초에 이슈가 필요한 갈래인지 루트 `CLAUDE.md` §워크플로의 type+path 표로 되돌아가 확인한다.

```markdown
# issue-{N}: {제목}

- Issue: https://github.com/groovallstar/ner-pipeline/issues/{N}
- PR: <!-- 머지 직전 채움 -->
- 브랜치: `feat/issue-{N}-{슬러그}`
- 승인일: YYYY-MM-DD

## 배경 (왜)                     [필수]  <!-- '동기'·'문제'·'근본 원인' 등으로 개명 가능 -->
<!-- 왜 지금 이 이슈가 필요한가 — 현재 무엇이 문제·공백·거짓 안심인가.
     있으면 측정값·재현 경로를 함께. 도달 상태(§목적)와 섞지 않는다 -->

## 목적                          [필수]
<!-- 측정 가능한 goal — 1~3줄. metric 으로 표현 -->

## 범위                          [권장]
- 포함:
- 제외:  <!-- 명시적으로 빠진 것. drift 방지 -->

## 성공 기준                     [필수]
- [ ] 테스트:
- [ ] 문서 갱신:
- [ ] 메트릭/검증:  <!-- falsifiable test. §검증의 AC로 흡수해도 됨 -->

## 위험·의존성                   [옵션]
<!-- 외부 서비스·데이터·회귀 패턴 등 -->

## 현 상태 (fact)                [권장]
<!-- 측정값·데이터 상태·확정된 사실. plan 아님. drift 시 갱신 -->

## 결정 로그 (append-only)       [불변식]
<!-- 방향 전환·접근 변경 사유. YYYY-MM-DD: 한 줄. 과거 항목 수정·삭제 금지 -->

## 미해결 질문 (open question)   [옵션]
<!-- 다음 결정이 필요한 항목. 답이 나오면 결정 로그로 이동 -->

## 구현 단계 (가변)              [권장]  <!-- '계획' 등으로 개명 가능 -->
<!-- 현재 최선의 plan. drift 시 그대로 수정 + 결정 로그에 사유 한 줄 -->
- [ ] 1.
- [ ] 2.

---

<!-- 이하 섹션은 5단계(PR 직전)에서 추가 작성 -->

## 변경 요약                     [옵션]  <!-- '구현 결과' 등으로 개명 가능 -->
<!-- 무엇을 어떻게 바꿨는가 — 3~5줄 -->

## 검증                          [필수]
- 테스트: 명령어 / 결과 (pass·fail)
- 메트릭: 변경 전후 비교 — 상세 표는 `docs/reports/` 에 두고 본 doc 은 link 만

## 관련 커밋                     [옵션]
- `<hash>`:
- `<hash>`:

## 후속 작업                     [옵션]
<!-- 분리된 이슈 번호 또는 TODO. 본 이슈 lifecycle 종료, 다음으로 넘김 -->
```

## 주의

- `docs/issues/` 는 **lifecycle-bound 보관소** 다. cold-start 핸드오프·미래 예측 섹션은 만들지 않는다. 실험 결과 상세 (메트릭 표·ablation) 는 `docs/reports/` 의 실험 보고서 형태로 분리하고 본 doc 은 결론 + link 만 둔다.
- plan 이 흔들리면 §결정 로그 에 한 줄 추가. plan 자체는 자유롭게 수정. *과거 결정 항목은 절대 수정·삭제하지 않는다*.
- 타 `docs/` 폴더와 역할이 겹치지 않게 한다. 이 폴더는 **이슈별 히스토리**만 담고, 도메인 지식·실행 가이드·엔티티 스펙 등은 해당 폴더에 맡긴다. 전체 구조는 루트 `CLAUDE.md` §핵심 디렉토리 구조 의 표 참조.
