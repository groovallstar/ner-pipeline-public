## 배경 (왜)

네 언어 코퍼스 모두 EMAIL gold 의 약 절반이 `32Rebecca.Thompson@gmail.com` 처럼
숫자로 시작한다. 실제 이메일에 없는 표면형이다. 학습 분포의 절반이 비현실 표면형이면
실사용 recall 이 깎이고, EMAIL metric 의 절반도 같은 표면형 위에서 재므로 숫자가
실제보다 낙관적이다. 지금은 EMAIL F1 이 0.98 이어도 그 값이 실사용 탐지를 보증하지
않는다.

경계 결함이 아니다. 원문 텍스트와 gold span 은 서로 맞고, 주입 문자열 자체가 그렇게
생성됐다.

## 목적

주입 EMAIL 로컬파트가 실제 이메일 표면형 분포를 따른다. 네 언어 전부에서 숫자 접두
비율 ≤ 5%, 재학습 후 EMAIL F1 무회귀.

## 범위

- 포함: EMAIL 주입기의 로컬파트 생성, 네 언어 코퍼스의 EMAIL 표면 치환·재학습·재측정.
- 제외: 도메인 목록(ko·ja 가 공용 목록을 써 `@yahoo.com.vn` 이 섞이는 별건),
  PHONE·ID_NUM·CREDIT_CARD 표면형 감사, 언어별 recall 결함.

## 근본 원인

`src/ner/augmenters/pii/generators/base.py` 의 `random_email()` 한 함수다.

```python
if r.random() < 0.5:
    local = normalize(local + random_digits(r.randint(1, 3), r))   # 접미
else:
    local = normalize(random_digits(r.randint(1, 2), r) + local)   # 접두
```

50/50 분기의 `else` 가 숫자를 로컬파트 앞에 붙인다. 이 분기 하나가 세 가지 결함을
한꺼번에 만든다.

1. **숫자 접두 50%** — `else` 가 뽑히는 비율 그대로다.
2. **숫자 포함 100%** — 두 갈래 어느 쪽이든 숫자가 붙어, 숫자 없는 로컬파트가 0건이다.
3. **점·대문자 100% (en·vi)** — 이름 힌트의 공백을 점으로 바꾸고(`hint.replace(' ', '.')`)
   이름 목록이 대문자로 시작하므로, `alice@` 같은 소문자 단일 토큰이 학습에 한 번도
   안 나온다. #263 이 재현한 en 미탐지의 gold 쪽 원인이 이 줄이다.

ko·ja 는 로컬파트가 `hftrx_cka7` 같은 무작위 자모 나열이다. CJK 이름 힌트가 ASCII
필터에서 전량 탈락해 `random_letters(8)` 로 대체되기 때문이며, 실제 표면형이 아닌 점은
접두 숫자와 같다.

## 현 상태 (fact)

생성기를 2만 회 돌린 분포가 배포 코퍼스 측정값과 자릿수까지 맞는다. 코퍼스 쪽은
`/data/ner/{lang}/data/`(2026-09-09 측정, 재측정 2026-09-10 동일), 생성기 쪽은
`generate_pii('EMAIL', lang, Random(42))` 2만 회다.

| 언어 | 숫자 접두 (생성기 / train) | 점 포함 | 대문자 포함 | 숫자 포함 |
|---|---|---|---|---|
| en | 49.9% / 49.0% | 100% | 100% | 100% |
| ko | 50.5% / 49.8% | 10% | 0% | 100% |
| ja | 49.9% / 50.6% | 10% | 0% | 100% |
| vi | 49.9% / 50.1% | 100% | 100% | 100% |

test 분할도 같다(en 48.8%, ko 51.2%, ja 48.3%, vi 42.9%).

학습 원천은 언어별 `data/{ontonotes_en,klue,stockmark,wikiann_vi}/origin.jsonl` 이고
`/data/ner/{lang}/data/` 는 거기서 결정적으로 재유도된 분할이다. en 학습 실측 21분
(`train_time_sec` 1265.7).

## 목표 분포

로컬파트를 **형태·대소문자·숫자** 세 축으로 나눠 각각 독립 추첨한다. 세 축이 독립이라
형태별로 대소문자 표를 다시 만들 필요가 없고, 축 하나를 조정해도 나머지가 안 흔들린다.

형태 축은 이름 두 토큰을 어떻게 잇는지가 정한다.

| 형태 | 비율 | 예 |
|---|---|---|
| 점 연결 | 30% | `emily.thompson` |
| 붙여쓰기 | 22% | `emilythompson` |
| 단일 토큰 | 20% | `emily` |
| 이니셜 + 성 | 15% | `ethompson` |
| 밑줄 연결 | 8% | `emily_thompson` |
| 하이픈 연결 | 5% | `emily-thompson` |

대소문자 축과 숫자 축은 형태와 무관하게 걸린다.

| 축 | 값 | 비율 |
|---|---|---|
| 대소문자 | 전부 소문자 | 90% |
| | 토큰 첫 글자 대문자 | 10% |
| 숫자 | 없음 | 72% |
| | 접미 1~4자리 | 26% |
| | 접두 1~2자리 | 2% |

접두를 0 이 아니라 2% 로 두는 것은 숫자로 시작하는 이메일이 드물지만 실재하기
때문이다. 학습에서 완전히 지우면 그 표면형이 다시 분포 밖이 되어, 지금 en 이
`alice@` 를 못 잡는 것과 같은 구멍이 반대편에 생긴다.

이 분포에서 점 없는 소문자 로컬파트는 약 63%(형태 70% × 소문자 90%)이고, 그중 단일
토큰만 봐도 18% 다. #263 이 요구한 `alice@example.com` 형태가 학습에 들어온다.

## 구현 단계

| 단계 | 하는 일 | 산출 |
|---|---|---|
| 1 | 목표 분포를 검사하는 테스트를 먼저 실패시킨다 | `tests/ner/augmenters/pii/test_email_localpart.py` |
| 2 | `random_email()` 로컬파트 생성을 목표 분포로 교체하고, ko·ja 에 로마자 이름 목록을 넣는다 | `generators/{base,ko,ja}.py` |
| 3 | `origin.jsonl` 의 EMAIL span 로컬파트만 치환하고 뒤따르는 오프셋을 재계산한다 | `scripts/rewrite_email_localpart.py` + 원장 |
| 4 | 네 언어 재학습·포장 | `results/classifier/{lang}/...`, `/data/ner/{lang}/` |
| 5 | 옛 모델을 새 test 로 다시 재고 새 모델과 나란히 둔다 | 이 문서 §검증 |

3 단계에서 도메인은 건드리지 않고 로컬파트만 바꾼다. 문맥·다른 라벨·도메인이 그대로면
전후 차이의 원인이 EMAIL 로컬파트 하나로 좁혀지고, LLM 자연 주입을 다시 돌릴 때처럼
코퍼스 전체가 함께 바뀌지 않는다.

## 성공 기준

- [ ] 생성기 분포 테스트 — 네 언어 각각 숫자 접두 ≤ 5%, 점 없는 소문자 로컬파트 ≥ 10%
- [ ] 재생성 코퍼스 — 네 언어 train·test 각각 숫자 접두 ≤ 5%
- [ ] 목표 분포를 문서에 명시 — 점 있음/없음, 대소문자, 숫자 포함 비율
- [ ] 재학습 후 EMAIL F1 무회귀 — 옛 모델을 새 test 로 다시 재 같은 기준으로 비교
- [ ] `docs/manual/pipeline/2-augmentation.md` 주입 스펙 갱신

## 결정 로그 (append-only)

- 2026-09-10: #263 과 합치지 않는다. 두 이슈가 같은 함수의 다른 줄에서 나오지만,
  #263 은 en 만 실패하고 vi 는 점 100% 인데도 통과하는 이유를 가려야 해 주입 분포
  수정만으로 닫히지 않는다. #262 가 주입기·코퍼스·재학습을 맡고, #263 은 재학습된 en
  모델에 probe set 을 물려 원인이 분포였는지 확인한 뒤 따로 닫는다.
- 2026-09-10: 코퍼스는 LLM 자연 주입 재실행이 아니라 `origin.jsonl` 의 EMAIL 표면
  치환으로 다시 만든다. 재실행은 비결정적이라 EMAIL 외 모든 것이 함께 바뀌고, 그러면
  무회귀 비교에서 원인을 EMAIL 표면형으로 좁힐 수 없다.
- 2026-09-10: ko·ja 로컬파트의 무작위 자모 나열도 같이 고친다. 목적이 실제 이메일
  표면형 분포라, `hftrx_cka7` 은 접두 숫자와 같은 결함이다.
- 2026-09-10: 목표 분포는 `docs/manual/data/` 가 아니라
  `docs/manual/pipeline/2-augmentation.md` 에 둔다. canonical 스키마 문서는 정의만
  담고 생성 규칙은 주입 단계 문서가 갖는 기존 분담을 따른다.
