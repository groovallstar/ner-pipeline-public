## 배경 (왜)

네 언어 코퍼스 모두 EMAIL gold 의 약 절반이 `32Rebecca.Thompson@gmail.com` 처럼
숫자로 시작한다. 실제 이메일에 없는 표면형이다. 학습 분포의 절반이 비현실 표면형이면
실사용 recall 이 깎이고, EMAIL metric 의 절반도 같은 표면형 위에서 재므로 숫자가
실제보다 낙관적이다. 지금은 EMAIL F1 이 0.98 이어도 그 값이 실사용 탐지를 보증하지
않는다.

경계 결함이 아니다. 원문 텍스트와 gold span 은 서로 맞고, 주입 문자열 자체가 그렇게
생성됐다.

## 목적

주입 EMAIL 로컬파트가 실제 이메일 표면형 분포를 따른다. 네 언어 전부에서 숫자 접두
비율 ≤ 5%, 재학습 후 EMAIL F1 무회귀.

## 범위

- 포함: EMAIL 주입기의 로컬파트 생성, 네 언어 코퍼스의 EMAIL 표면 치환·재학습·재측정.
- 제외: 도메인 목록(ko·ja 가 공용 목록을 써 `@yahoo.com.vn` 이 섞이는 별건),
  PHONE·ID_NUM·CREDIT_CARD 표면형 감사, 언어별 recall 결함.

## 근본 원인

`src/ner/augmenters/pii/generators/base.py` 의 `random_email()` 한 함수다.

```python
if r.random() < 0.5:
    local = normalize(local + random_digits(r.randint(1, 3), r))   # 접미
else:
    local = normalize(random_digits(r.randint(1, 2), r) + local)   # 접두
```

50/50 분기의 `else` 가 숫자를 로컬파트 앞에 붙인다. 이 분기 하나가 세 가지 결함을
한꺼번에 만든다.

1. **숫자 접두 50%** — `else` 가 뽑히는 비율 그대로다.
2. **숫자 포함 100%** — 두 갈래 어느 쪽이든 숫자가 붙어, 숫자 없는 로컬파트가 0건이다.
3. **점·대문자 100% (en·vi)** — 이름 힌트의 공백을 점으로 바꾸고(`hint.replace(' ', '.')`)
   이름 목록이 대문자로 시작하므로, `alice@` 같은 소문자 단일 토큰이 학습에 한 번도
   안 나온다. #263 이 재현한 en 미탐지의 gold 쪽 원인이 이 줄이다.

ko·ja 는 로컬파트가 `hftrx_cka7` 같은 무작위 자모 나열이다. CJK 이름 힌트가 ASCII
필터에서 전량 탈락해 `random_letters(8)` 로 대체되기 때문이며, 실제 표면형이 아닌 점은
접두 숫자와 같다.

본 적 없는 test 라는 조건은 만족한다.

## 목표 분포

로컬파트를 **형태·대소문자·숫자** 세 축으로 나눠 각각 독립 추첨한다. 세 축이 독립이라
형태별로 대소문자 표를 다시 만들 필요가 없고, 축 하나를 조정해도 나머지가 안 흔들린다.

형태 축은 이름 두 토큰을 어떻게 잇는지가 정한다.

| 형태 | 비율 | 예 |
|---|---|---|
| 점 연결 | 30% | `emily.thompson` |
| 붙여쓰기 | 22% | `emilythompson` |
| 단일 토큰 | 20% | `emily` |
| 이니셜 + 성 | 15% | `ethompson` |
| 밑줄 연결 | 8% | `emily_thompson` |
| 하이픈 연결 | 5% | `emily-thompson` |

대소문자 축과 숫자 축은 형태와 무관하게 걸린다.

| 축 | 값 | 비율 |
|---|---|---|
| 대소문자 | 전부 소문자 | 90% |
| | 토큰 첫 글자 대문자 | 10% |
| 숫자 | 없음 | 72% |
| | 접미 1~4자리 | 26% |
| | 접두 1~2자리 | 2% |

접두를 0 이 아니라 2% 로 두는 것은 숫자로 시작하는 이메일이 드물지만 실재하기
때문이다. 학습에서 완전히 지우면 그 표면형이 다시 분포 밖이 되어, 지금 en 이
`alice@` 를 못 잡는 것과 같은 구멍이 반대편에 생긴다.

이 분포에서 점 없는 소문자 로컬파트는 약 63%(형태 70% × 소문자 90%)이고, 그중 단일
토큰만 봐도 18% 다. #263 이 요구한 `alice@example.com` 형태가 학습에 들어온다.

## 검증

측정일 2026-09-10. 학습·포장은 `python -m ner.classifier` + `build_ner_prod.py`,
평가는 학습 경로와 같은 `evaluate_model` + `compute_offset_span_f1` 을 쓰는 임시
스크립트로 test 전수를 쟀다. 배포 eval 스크립트를 안 쓴 것은 ja·vi 판이 앞 100문장만
재고 타입별 표를 안 내기 때문이다. 임계값은 양쪽 모두 미적용(raw)이다.

### 기준 1. 생성기·코퍼스 분포

`uv run pytest tests/ner -q` 886 passed. 배포 분할의 EMAIL 로컬파트 숫자 접두는
train·valid·test 열두 조각 전부 ≤ 2.9% 다(en train 2.09% · ko train 2.03% ·
ja train 1.93% · vi train 2.08%, 최댓값 ja valid 2.86%).

### 기준 2. 같은 새 test 위의 옛 모델·새 모델

같은 test·같은 평가 코드로 두 모델을 잰 값이다. 옛 모델은
`/data/ner/_pre-issue-262/{lang}/model` 로 보존했다. 2026-09-18 에는 그 경로가 없고,
en·ko 옛 번들만 `/data/ner/{en,ko}.tar.gz` 로 남아 있다(`metrics.json` 의 데이터 지문이
치환 전 값 `258166d6972c8144`·`a6aaa31ba099c9fd` 다). ja·vi 는 이 표를 다시 잴 수 없다.

| 언어 | test 행 | EMAIL span | EMAIL 옛 → 새 | overall 옛 → 새 |
|---|---:|---:|---|---|
| en | 7,637 | 2,385 | 0.8937 → **0.9943** | 0.9163 → 0.9288 |
| ko | 2,598 | 887 | 0.9989 → **0.9989** | 0.9156 → 0.9275 |
| ja | 100 | 26 | 1.0000 → **1.0000** | 0.9729 → 0.9346 |
| vi | 3,774 | 716 | 0.9979 → **1.0000** | 0.9479 → 0.9521 |

**ja 의 overall 비교는 쓸 수 없다.** 누출 가드 때문에 분할 방식이 바뀌어 새 test
100행 중 95행이 옛 모델의 train·valid 에 있었다. 편향이 옛 모델 쪽이므로 EMAIL 이
양쪽 1.0 인 것은 유효하지만, overall 하락분은 노출 차이지 회귀가 아니다.

### 기준 3. en 표면형별 득실

en test 2,385 EMAIL span 을 로컬파트 표면형으로 묶은 strict recall 이다.

| 표면형 | support | 옛 모델 | 새 모델 |
|---|---:|---:|---:|
| 붙여쓰기 소문자 | 877 | 0.806 | **1.000** |
| 붙여쓰기 + 숫자 | 364 | 0.898 | **1.000** |
| 밑줄·하이픈 | 264 | 0.992 | 1.000 |
| 붙여쓰기 대문자 | 96 | 1.000 | 1.000 |
| 점 포함 | 729 | 0.997 | 0.986 |
| 숫자 접두 | 55 | 1.000 | 0.964 |

옛 모델의 결손이 점 없는 소문자(0.806)와 붙여쓰기+숫자(0.898)에 몰려 있었고, 그 두
칸이 #263 이 재현한 미탐지의 정체다. 새 모델은 두 칸을 1.000 으로 올리는 대신 숫자
접두에서 55건 중 2건, 점 포함에서 729건 중 10건을 잃었다. 학습 비중이 49% 에서 2% 로
내려간 표면형이 완벽을 유지하지 못하는 것은 예상된 대가이며, 분포 안에 남겨 둔 이유는
§목표 분포에 적었다.

### 기준 4. #263 probe

#263 재현 문장 + 표면형 축 13건을 서버 추론 경로(`LangModel.predict`, raw)로 물렸다.
strict 일치 기준 옛 모델 8/13, 새 모델 11/13. 옛 모델이 놓치던 `alice@example.com`·
`alice@gmail.com`·`emilythompson@yahoo.com` 을 새 모델이 전부 잡는다. **#263 의 원인은
(a) 주입 표면형 분포다** — BPE 분절이 원인이면 코퍼스만 바꿔서는 안 고쳐진다.

새 모델이 놓친 둘은 성격이 다르다. `Contact her (email alice@example.com) before
Friday.` 는 탐지가 아니라 경계 문제로 `@example.` 까지만 잡고, `32Rebecca.Thompson@
gmail.com` 은 숫자 접두 + 점 + 대문자가 겹친 형태다. 둘 다 #263 에서 probe set 을
테스트로 고정할 때 다룬다.

### 기준 5. 출하 번들

네 언어 모두 `build_ner_prod.py` 로 다시 포장하고 서버 로드 경로로 확인했다. en·ko·vi
는 raw, ja 는 새 run 에서 다시 fit 한 `thresholds.json` 을 싣는다. vi 는 배포와 같은
PhoBERT slow 토크나이저로 열리고, 네 언어 모두 EMAIL 을 정상 탐지한다.

### 청크 경계가 엔티티를 가르던 부수 발견

vi 번들의 test 가 101행에서 3,774행이 되고 EMAIL 문자열 길이가 바뀌면서 장문 청킹의
경계 위치가 밀렸고, `Do You Know ? ( The Ping Pong Song )` 이라는 PROD 엔티티가 경계에
걸렸다. 같은 3,774행을 치환 전 코퍼스로 재면 걸림이 0건이라 원인은 표면형이 아니라
경계 위치다. 서버 청킹이 `?` 를 문장 끝으로 본 것이 결함이며, 경계 문자 뒤 첫 비공백이
여는 괄호이거나 소문자면 문장이 안 끝난 것으로 보게 고쳤다. 배포 test 전수로 재면 네
언어 모두 걸림 0건이고 청크 수는 en 1,239 → 1,255, ko 586 → 587, ja 25 → 25,
vi 452 → 460 이다.

### 남는 한계

- ko 는 train-seed 42 run 이 EMAIL 에서 튀었다(test 0.9466 · valid 0.9566). 시드 43·44
  는 test 1.0000·0.9989, valid 둘 다 1.0000 이다. 출하는 **valid EMAIL F1 을 1순위,
  valid overall 을 동점 처리 기준**으로 골라 seed 44 로 했다. test 를 보고 고르지
